# open_area: the one call an agent makes when it opens an area

> Read before touching `open_area` (`src/plugins/kelno_vault/open_area.py`, `area_result.py`, `areas_index.py` beside it). Fork-only (see `FORK.md`). Since 2026-11-13 it is a tool of the `kelno_vault` plugin (`Plugin.tools`, see [plugins](plugins.md)): the core registers it, wrapped in `_tracked` like its own tools, and serves it only when that plugin is loaded.

An agent starting work in an area, or answering a question about one, used to make several calls (read the main note, `ledger_search(area=…)`, `list_tasks(area=…)`) and could skip any of them; one skipped call is how a postponed decision recorded elsewhere went unseen (ledger F60). `open_area` returns all of it in one result, with two lines saying what to do with it. Owner's design (2026-11-12), following the tenet that a tool should give an agent what it needs at the moment of choice rather than rely on the agent remembering a rule.

## Input

- `area`: a slug, a tag (`#area/x`) or the main note's name, resolved like `list_tasks(area=…)` (`task_query.AreaIndex.lookup`): an area is a note whose frontmatter declares `area_tag`.
- `folder`: an absolute path outside the vault (a repo, a working directory). Resolved through the vault's list of areas (`AREAS_INDEX_PATH`, a constant of the plugin: `Areas/Areas.md`; until 2026-11-13 a core setting, a leftover value is ignored): a Markdown table whose "Related folders" column lists absolute paths in code spans and whose "Vault folder" column links the main note. Paths compare case-insensitively with `\` and `/` alike, and a subfolder of a listed folder matches (the deepest listed folder wins). The list is the only link between a folder and an area: repos never point into the vault.

Exactly one of the two. A folder no row lists: `found: false` and a note to ask the owner which area it belongs to. A folder listed under two areas at the same depth: `found: false`, naming both. A row whose area has no main note yet (or whose note declares no `area_tag`): `found: true` with the row's name and folders, and a note.

## Output, in order

1. `area`, `tag`, `name` (the row's), `description` (frontmatter), `code_project` (true when the main note's frontmatter sets `code_project: true`, read from disk with the note at each call; any other value, a string `"true"` included, or broken frontmatter: no field. Owner's decision, 2026-11-17: the vault marks the areas worked as code projects with this flag, which `main_note_text` leaves out with the rest of the frontmatter, so agents saw it nowhere; the plugin's `CODE_PROJECT_FIELD`, an outside dependency in the vault), `main_note`, `main_note_open_url` (a link opening the main note in Obsidian, with `OPEN_NOTE_URL` set; see "Open-note links" in [vault tools](vault-tools.md)), `archived` (the main note is under `ARCHIVE_FOLDER`; unset: not reported), `matched_folder`.
2. `area_conventions`: the vault's conventions for working on any area, the `## Working on an area` section (level 2, matched case-insensitively, up to the next heading of level 1 or 2; `areas_index.section_body`) of the vault guide note, the note `VAULT_GUIDE_NOTE` names (the one `get_vault_guide` serves; see [vault tools](vault-tools.md)). Read from disk at every call, never copied into the code, so an edit of the note reaches the next call; the heading's name is the plugin's constant `OPEN_AREA_CONVENTIONS_HEADING`, recorded as an outside dependency in the vault. Cut at 8,000 characters with a note (4,000 until 2026-11-16, when the rules for work notes moved into the section; ledger P175). A missing note, a missing or empty section, or a read error is one line in `notes` and no field, never a refusal. Also returned for a folder whose area has no main note yet. Why: the section used to reach an agent only through a pointer in the vault's common rules; inside the result it reaches every session that opens an area (owner, 2026-11-15, ledger P163).
2a. `for_agents`, placed before `area_conventions`: the area's own rules for agents, the body of its main note's `## For agents` section (owner's decision, 2026-11-17: an area's standing rules live in that one section, before `## Current position`, so an agent opening the area meets them first, apart from the rest of the note). The heading is not a constant here: it is the section heading the vault's list of rule files names (`rule_files`, the note `_/Rule files.md`, read at each call; see "A rule edit with no proposal ref is pointed out" in [vault tools](vault-tools.md)), the same definition the rule-edit nudge and the vault's local edit guard read. Every such level-2 section is taken out of `main_note_text` (headings inside fenced code are not headings); their bodies, trimmed of blank lines, joined by a blank line. No section, or an empty one: no field and no note. Cut at 8,000 characters with a note naming `read_note(…, section=…)`. When the list of rule files can't be read: no field, the section stays in `main_note_text`, and one note says so.
3. `main_note_text`: the main note without its frontmatter, its `## For agents` section (above) and its `## Tasks` section (headings inside fenced code are not headings), so `## Current position` and the rest reach the agent; cut at 15,000 characters with `main_note_chars` and a note.
4. `related_folders`: from the area's row.
5. `map`: what the area's folder holds, so an agent knows which note to open without opening each one (owner's design, 2026-11-16). Built from the index (`notes_metadata`: path and the `description` frontmatter field, `area_map.DESCRIPTION_FIELD`, the field the area's own description comes from; the plugin reads it by name, independently of `LIST_NOTES_DESCRIPTION_FIELD`), by `area_map.build` (`src/plugins/kelno_vault/area_map.py`). The area's folder is the main note's, and only when the main note is that folder's folder note (`X/X.md`, any case); otherwise no map and a note. Lines, in order:
   - each note directly in the folder, the main note left out, by name: `Paint.md — "Which paint, where."`, or `Bare.md — no description`;
   - each direct subfolder, by name: `Log/ — 12 notes — "One note per day."` (the count is recursive and includes the folder note `Log/Log.md`, whose description it shows), or `…, no folder note (Old/Old.md)`, or `…, its folder note Ideas/Ideas.md has no description`;
   - at most `OPEN_AREA_MAP_MAX` (30) of those, then `N more not listed (a notes, b subfolders): list_notes(folder="<area folder>/") lists the area's notes.`;
   - when any note (listed or not) or existing folder note has no description: `N notes without a description: add one when you work on them.`;
   - when there is a subfolder, one line with one example, the first subfolder not private: `To list a subfolder's notes with their descriptions: list_notes(folder="<area folder>/Log/"), for example.` ("with their descriptions" only when `LIST_NOTES_DESCRIPTION_FIELD` is set, so `list_notes` shows them). Owner's decision: one example, never a call on every subfolder line.

   A description is a string value only (a date, list or number counts as none), whitespace runs made one space, cut at 300 characters, and rendered as one JSON string literal (`note_description`, shared with `list_notes`; `change_feed.quote`), so it cannot start a line of its own. A note in a private folder, or a private subfolder, is listed by name and count only, `in a private folder, description not shown` / `a private folder: description not shown`, like the tasks below; it never counts as lacking a description. No map (no field) when the folder holds nothing but the main note.
6. `entries`: the active ledger entries as `ledger_search(area=…)` lists them without a query (the same helper, `_ledger_listed`), entries tied by a topic marked `via_topic`, each with its task state; at most 40, newest change first, with a note pointing to `ledger_search` for the rest.
7. `tasks`: open tasks, each with its `id` (its `🆔`, the name to change or cite it by) and `path:line` (status type not DONE, CANCELLED or NON_TASK, read with the owner's Tasks settings) carrying the area's tag or a tag under it, in any note: `#next` first, then by urgency, at most 30 with `tasks_total` and a note pointing to `list_tasks(area=…)`. Each listed line is checked on disk like `list_tasks` (a changed line is left out and counted in a note). A task in a private folder (`PRIVATE_FOLDER_NAMES`, one definition for every tool: "Private folders" in [search](search.md)) shows `path:line` and status only, as in the ledger's `cited_by`, with no argument to open it: a note points to `list_tasks(area=…, include_private=true)`. Without the setting nothing is private.
8. `instructions`: three lines, one for starting work (check each task and entry against it: related, for the owner, done or made stale, the event a `#when` task waits for), one for a status question (report the Current position and the `#next` tasks), and one telling an agent starting a piece of work that will span several conversations to give it a work note: the rules are under "Work notes" in `area_conventions`, and the template (`_/agent/templates/Work note.md`) is a starting point to copy and adapt (ledger P135, P175).
9. `notes`: first, the area's open feedback whose citing tasks are all done (the owner may have ticked them in Obsidian, where no tool runs), with the next step: close each as `handled`, unless something in it is still open, and tell the owner (ledger F51; see "Task links" in [agent ledger](agent-ledger.md)). Then anything that could not be read (the list of areas, the vault guide note or its section, the main note, the tasks, the entries) is a note, never a refusal: the rest still answers.

The tag match is exact (`#area/x` or `#area/x/…`), unlike `list_tasks(area=…)`, which follows the plugin's substring match and says when it overlaps another area.

## Writes in an area not opened

Ledger F89 (2026-11-14): a `keyword_search` led an agent straight to two notes inside an area's folder, and it edited them without ever calling `open_area`, so it missed the area's rules (its main note's `agent_managed: true`). The rule to start with `open_area` was in its instructions; nothing in the flow brought it back. So the plugin's write hooks point it out (`area_opened.py`): a note write (`create_note`, `edit_note`, `write_file` on a `.md`, through the `rewrite` report; `move_note`'s destination, through `check_name`) inside an area's folder (`AreaIndex.area_for_path`, the deepest area folder holding the path, as `create_task` infers its area), when the caller hasn't called `open_area` for that area in the last hour (`WINDOW_SECONDS`), gets `area_not_opened:` naming the area and the `open_area` call to make. Every such write gets it until the area is opened: repeating costs a few lines, and the agent ends it by doing what it says. Never a refusal (owner's direction: little effort; scripts and quick edits the owner asked for must go through). Any failure (an index that can't be read, a folder claimed by two areas) says nothing.

"The caller" is `(current_principal, user id)`: the API key or the OAuth grant. The MCP transport is stateless (`stateless_http=True`), so there is no session to key on. `open_area` records the area it found (tool function, after `open_area_impl`); the map is in-process, bounded by `MAX_ENTRIES`, oldest dropped first.

## Later parts

The function is one helper per part (`_open_area_main_note`, `_open_area_map`, `_open_area_entries`, `_open_area_tasks`), so later parts go beside them: notes changed since an agent last looked, hints for tasks that look stale, and matching a "When …" task's trigger against the work being started.

## Accepted limitations

| # | What | Why accepted |
| --- | --- | --- |
| A1 | Tasks come from the task index, minutes behind a hand edit; a listed line is checked on disk, but a task added by hand since the last pass is missing. | Same as `list_tasks`. |
| A2 | The list of areas is read as written: a folder outside a code span, or a row in a second table, is not seen. | The note is kept by agents under the vault's rules; a missing match says to ask the owner. |
| A3 | The map comes from the index, minutes behind a hand edit: a note created or described since the last pass is missing or shows its old description. An area whose main note is not its folder's folder note gets no map. | Same lag as `list_notes`; the vault keeps every area as `Areas/<Name>/<Name>.md`, and a main note elsewhere has no folder that is the area's alone. |
| A4 | `for_agents` keeps a CRLF note's line endings; a lone-CR note's section is not found, so its rules stay in `main_note_text`; with two `## For agents` sections the cut note names the heading, which `read_note(section=…)` resolves to the first. | Cosmetic, and nothing is lost (adversarial review, 2026-11-17). |
| A5 | `area_not_opened:` keys on the credential, not the conversation: one OAuth grant (claude.ai's connector, probably shared by the owner's conversations; not verified) that opened an area in one conversation silences the nudge in another for an hour. | The transport has no session; the window keeps it short. |
| A6 | The memory of opened areas is lost on a restart (the nudge then shows once more) and is per worker (`--workers 1` is the contract anyway). | A wrong nudge costs one `open_area` call. |
| A7 | `set_frontmatter` and the task writers get no nudge: the plugin has no hook there. | Writes reached from a search hit are note edits; adding hooks for this is more than the owner wanted spent. |
| A8 | Nested areas count apart: the nudge names the deepest area holding the note, and opening its parent area doesn't silence it (nor the reverse). An edit that changes nothing, and a move within an area not opened, also get it (adversarial review, 2026-11-14). | The text stays true in each case; the cost is one `open_area` call. |

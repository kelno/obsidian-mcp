# Calendar tools (the `caldav` plugin)

Five tools that read and change calendars on a CalDAV server: `list_calendars`, `list_events`, `create_event`, `update_event`, `delete_event`. They are a plugin (`src/plugins/caldav/`, loaded by naming `caldav` in `PLUGINS`), generic to any CalDAV server and any vault, and written against Nextcloud. They touch no note: the plugin fills the `tools` and `guide_text` hooks, and `startup` to open its session in the background (below). The core registers the tools and wraps each in `_tracked` like its own.

| Module | Holds |
| --- | --- |
| `config.py` | the `CALDAV_*` settings and `problems()`, what keeps the tools from working |
| `client.py` | a small CalDAV client (RFC 4791) over httpx: discovery, calendars, the expanded query, GET, PUT, DELETE; the shared session per login and the kept calendar list and repeat rules |
| `ical.py` | the iCalendar work, pure: reading occurrences, building and changing events, times and time zones |
| `result.py` | the structured results |
| `tools.py` | the five tools, their descriptions, and the rules below |

## Decisions

- **Only when the user asks** (the owner's decision, 2026-11-14). The first line of each tool's description and the guide's section say the tools are used only when the user asks about their calendar or schedule, or to add, change or remove an event, never on an agent's own initiative. How a deployment's agents should use the calendar (with tasks, for planning) is the deployment's to decide later; until then the tools are there for the user's requests only.

- **httpx and icalendar, not the `caldav` library.** The `caldav` client (3.x) is synchronous and brings lxml, niquests, dnspython, pyyaml and more. The tools need five kinds of request, which httpx (already here) sends with the core's transport policy. `icalendar` (BSD-2) reads and writes the event format, which is fragile to do by hand (escaping, folding, time zones). Chosen by the build session on 2026-11-14; the owner may revisit it.
- **The server expands repeating events.** `list_events` sends `calendar-query` with `expand` (RFC 4791 §9.6.5): the server returns one VEVENT per occurrence, in UTC, with `RECURRENCE-ID` on each occurrence of a repeating event. Its own recurrence engine (sabre/dav on Nextcloud) decides, so the tools need no expansion library and agree with what calendar apps show. A server that ignores `expand` returns the stored event, still carrying its rule: such an event is left out with a note, never listed at its first date (which may be years outside the range). The repeat rule shown on each occurrence comes from one `calendar-multiget` of the repeating events' stored objects.
- **Settings are read per call, and a problem is a refusal, not a server that does not start.** A missing `CALDAV_URL`, `CALDAV_USERNAME` or `CALDAV_PASSWORD`, an http address to another machine, an unknown time zone, a refused login (401) or a redirect each answer `calendar_not_configured`, naming what to fix. This differs from the plugin rule that a name in `PLUGINS` which does not load stops the server: that rule protects a vault's guards, and a calendar not set up yet endangers nothing, while the vault tools stay usable.
- **Single-user deployments only.** One CalDAV login serves the whole deployment; with `MULTI_USER_MODE` on, every user would see one person's calendars, so the tools refuse (`calendar_not_configured`).
- **Which calendars.** The tools work with the event calendars the login sees (shared ones included), or only those `CALDAV_CALENDARS` names, in that order. Task lists (no VEVENT in `supported-calendar-component-set`) are left out. An event id naming any other calendar is refused before any request reaches it. A calendar is named (in the setting or by an agent) by its id, its name in any case, or its name without the ` (owner)` Nextcloud appends to a calendar shared with the login ("Patipa (kelno)"); several matches are refused, listing their ids. Writability comes from `current-user-privilege-set`; a 403 on a write is also `calendar_read_only`. The calendar that takes new events when none is named: the first writable one in `CALDAV_CALENDARS`, else the only writable one, else none (`create_event` then needs `calendar`). This matters on Nextcloud, where a new user gets an empty "Personal" calendar of its own: an event put there is in no one else's calendar.
- **Event ids** are `<calendar id>/<object name>`, both as the server spells them in hrefs (percent-encoded). An id must be exactly two non-empty segments, neither `.` nor `..`, the name without an encoded `/` or `\`, before any request.
- **Writes keep what they do not change.** `update_event` and `delete_event` GET the object, change the parsed iCalendar and PUT it back whole with `If-Match` (its ETag): reminders, categories, attendees, other apps' `X-` fields and other occurrences' changes are kept, and a change made meanwhile is refused (412, `calendar_conflict`), never overwritten. `create_event` PUTs with `If-None-Match: *` at `<uuid>.ics`.
- **A repeating event is never changed or deleted whole by accident.** On one, `update_event` and `delete_event` need `occurrence` (that occurrence) or `all_occurrences=true` (the series, past occurrences included); with neither, `occurrence_required`. An occurrence is named by its original start, as `list_events` gives it in `occurrence`, and is checked against the server's expansion (or an existing override) first, so a wrong one is `not_found` rather than a silent no-op. Changing one occurrence writes an override (a VEVENT with `RECURRENCE-ID`, copied from the series with its reminders); deleting one adds an `EXDATE` and drops its override.
- **Moving a whole series is refused.** `start`/`end` with `all_occurrences` would move the series' first occurrence, and with it every past one; calendar apps split the series instead. Not built: the agent changes one occurrence or leaves it to the owner. The title, place, notes and rule of a series can change.
- **Events with attendees are left to the owner** (`event_has_attendees`): changing or deleting a meeting from a shared calendar may make the server mail its attendees.
- **Confidential and private events are left to the owner** (`event_not_editable`). Nextcloud serves a calendar's sharees an event marked `CLASS:CONFIDENTIAL` stripped (`CalendarObject::get()`): the title becomes "Busy", and only the times, the rule and a few ids stay; place, notes, reminders and other apps' fields are gone, and the ETag is the whole event's. A change PUT back, or an `EXDATE` added, would be accepted and erase the rest. So `update_event` and `delete_event` refuse an object with any VEVENT whose `CLASS` is CONFIDENTIAL or PRIVATE, also on a calendar the login owns, where nothing is stripped: the tools cannot tell in general whose calendar it is. `list_events` marks such events `confidential`. Found by the adversarial review (2026-11-14).
- **Events with floating times are not changed** (`event_not_editable`). A time without a zone (no `TZID`, no `Z`) is read by sabre in the calendar's `calendar-timezone`, else UTC, so an `EXDATE` or `RECURRENCE-ID` the tools write in `CALDAV_TIMEZONE` may name no occurrence and change nothing, silently. `update_event` and the deletion of one occurrence refuse them; deleting the whole event or series works, since it names no time.
- **All-day events and ranges.** sabre matches an all-day event against a range at midnight UTC, not in the calendar's zone: asked for 20 November in Brussels (from 19 November 23:00 UTC), it also answers with the 19th's all-day events, and west of UTC an evening range misses the day's. Every expanded query (`_occurrences`) asks the server a day wider on each side and keeps what overlaps the real range, an all-day event by the calendar zone's days (`_within`).
- **A series' new title, place or notes reach its changed occurrences.** A changed occurrence is a VEVENT of its own with its own copy of them; with `all_occurrences`, each one still holding the series' old value takes the new one, and one changed on purpose keeps its own (`ical.carry_to_overrides`).
- **A new place or new notes drop the apps' copies of the old ones**: `X-APPLE-STRUCTURED-LOCATION` and `GEO` with the place, `X-ALT-DESC` (the notes as HTML) with the notes, or an app would go on showing the old ones.
- **One calendar that cannot be read does not hide the others.** `list_events` lists the rest and names it in `notes`; only when every calendar fails is it a refusal. An object that cannot be read (not iCalendar, an event without a start) is left out with a note, here and in the duplicate and occurrence checks, so one broken event never blocks a create.
- **Deleting a series' last occurrence.** Nextcloud answers a series left with no occurrence with HTTP 500. Only then, and only on a series that has a last occurrence (every rule with `COUNT` or `UNTIL`, or set dates only), does that `calendar_unavailable` add: tell the owner, and delete the whole series only if they agree. Any other failure (a timeout, a 502, maintenance's 503) gets no such hint: an agent following it would delete a whole series, past included, because the server was down (independent review, 2026-11-14).
- **Stopping a series from a date on** keeps its past: `update_event` with `all_occurrences` and `repeat` set to its rule with `UNTIL`, as `delete_event` and its `occurrence_required` refusal say. Changed occurrences after the new `UNTIL` are removed (sabre would go on listing them), comparing dates for an all-day series and instants for a timed one; one exactly at `UNTIL` stays.
- **A duplicate is refused.** `create_event` first lists the target calendar over the new event's span; the same title (any case) at the same start is `duplicate_event`, naming the existing event. It catches an agent retrying a create whose answer it lost.
- **Times.** Times without an offset are read in the calendar's time zone (`CALDAV_TIMEZONE`, else `TASKS_TIMEZONE`), and every time shown is in it, with its offset. New and changed times are written with that zone's `TZID` and a `VTIMEZONE` (`icalendar`'s `add_missing_timezones`), so a weekly event keeps its local time across clock changes. An all-day event takes dates, and the tools speak in last days (`end` included); iCalendar's exclusive `DTEND` is converted in `ical.py` only. A repeat rule's `UNTIL` is fitted to the event's kind (a date for an all-day event, a UTC time otherwise).
- **Transport.** No redirects (the password would follow one; a redirect is reported with its target), `trust_env=False` (no proxy or `.netrc` from the environment), `OUTBOUND_USER_AGENT`, `CALDAV_TIMEOUT_SECONDS` for the whole call, at most 4 MB read from one response, and every request sent to `CALDAV_URL`'s own scheme and host whatever host a response's href names. The password reaches only the `Authorization` header: it is a `SecretStr`, the settings hide input in errors, and no result, log line or usage row holds it. Usage rows keep the calendar, times and event ids, never titles, places or notes.
- **Admission.** All five tools are `light`, the writers included: a calendar write waits on the calendar server, up to `CALDAV_TIMEOUT_SECONDS`, and in `write` it would hold the vault writers' single slot meanwhile, so under `queue` or `enforce` every note, task and ledger write would wait or be refused while Nextcloud hangs (independent review, 2026-11-14). The writers still draw on the write budget (`write_class`, which sets the rate bucket apart from the admission class), like the agent ledger's writers: no vault byte, but the owner's own data. They hold no database connection of their own beyond the usage row (`test_concurrency_tool_checkout_peaks_pg.py`).
- **One deadline per call.** `CALDAV_TIMEOUT_SECONDS` bounds all of a call's requests together (`asyncio.timeout_at` in the client), not each one: httpx's timeout is per phase of a request, and a write makes up to five. A write cut off by it may still have reached the server; listing again shows.
- **The server's session is kept between calls.** Nextcloud checks a login slowly and a session fast. Measured on the owner's Nextcloud (2026-11-18): a request without a login answered in 0.2 s, one that logs in in about 8 s, the first two of a new session in 7.7 and 10.8 s, every later one in 0.25 s; a call that logged in on each of its three requests ran out of time on logins alone. One httpx client per (`CALDAV_URL`, `CALDAV_USERNAME`) serves every call (`client._Session`, in memory, like the discovered home), so its connections (no new TLS handshake per call) and the server's session cookies go from one call to the next as they arrive, a failed or timed-out call's included. The login still goes with every request, so a session the server dropped costs one login, never a refusal. Until the session is established (a request came back without the server changing its cookies, or three came back), requests go one at a time: calls arriving together on a cold session, and `list_events`' parallel queries, wait for the one login under way rather than each paying their own. `CALDAV_TIMEOUT_SECONDS` defaults to 60 so the logins of a new session fit in one call. The cookies are a credential: memory only, never logged.
- **The session is opened at startup and kept warm** (`startup`, `tools.keep_warm`): after a restart, the first call paid the logins, some 18 s measured on the deployment. As the server starts serving, a background task lists the calendars (opening the session and filling the kept list below), then again every 30 minutes (`KEEP_WARM_SECONDS`) so a day without use does not let Nextcloud drop the session (`session_lifetime`, a day by default). Nothing is started when the settings have a problem (each call then refuses as before); a failed round is logged by its refusal code only and the next round tries again; the task closes the sessions when cancelled at shutdown. It costs the CalDAV server one 0.25 s request every 30 minutes.
- **The calendar list is reused for two minutes, never for a refusal** (`client.CALENDARS_MAX_AGE_SECONDS`): `list_events` and the writers work from the list fetched in the last two minutes, saving a request (0.25 s) per call; `list_calendars` always asks the server, and refreshes the kept list. Every refusal about a calendar (no such calendar, several, read-only, no default) comes from a list asked of the server now: when the kept list would refuse, the call asks again and decides on the fresh one (`tools._choose`), so a calendar made in the owner's app a minute ago is found. Any failed request drops the kept list. The tools never create, delete, rename or share a calendar, so nothing they do makes the kept list stale; what remains is in "Accepted limitations".
- **A repeat rule is read once per version of its event.** The rule shown on each occurrence comes from the stored object (`calendar-multiget`); the rule read is kept per object and ETag (`client.RULES`, at most 5,000, then started over), and reused while the expanded query gives the object the same ETag, which names one version of it, so `list_events` skips the second request per calendar when no repeating event changed. A rule is kept only when the multiget's ETag is the one the expanded query gave.
- **Answers are parsed off the event loop** (`asyncio.to_thread`, as `fetch_page` does), and at most 4 MB is read from one: measured in the test image, 5,000 occurrences take 1.7 s to read and 20,000 (7.4 MB) some 160 MB of memory, which would stall every other call of the one worker. A year of a busy calendar is about 1,000 occurrences.
- **Who sees the writers.** The core's write registry (`tool_permissions.WRITE_REQUIRED_TOOLS`) is a fixed list of core tools, so a read-only OAuth grant is shown the three calendar writers; each calls `_require_write()` first and refuses such a caller (`permission_denied`) before any request.

## Accepted limitations

- No reminders, attendees or invitations are created; no time zone other than the calendar's is written.
- Moving a whole repeating series is not supported (above), nor changing "this and the following" occurrences.
- Discovery (the principal and calendar home) is cached per process and per `CALDAV_URL` and user; a server that moves the calendar home needs a restart.
- A calendar changed outside the tools (in the owner's app or Nextcloud's web page) may be seen as it was for up to two minutes by `list_events` and the writers, never by `list_calendars`: one created or shared meanwhile is missing from a `list_events` over all calendars (named, it is found); one renamed shows its old name; one deleted, unshared or made read-only gets the server's error rather than the tools' own refusal (`not_found`, `calendar_unavailable` or `calendar_read_only`, worded as the server's; in a `list_events` over all calendars, a note that it could not be read), which drops the kept list; and when `CALDAV_CALENDARS` is unset, a writable calendar added meanwhile does not yet take away the default for new events. While the server is down, a `list_events` over the kept list says it could not reach the server for the events rather than for the calendars (the same `calendar_unavailable`).
- A server that does not support `expand` lists no repeating event (with a note).
- XML from the server is parsed with the standard library's `ElementTree`; the server is the deployment's own, named by its owner, so its answers are not treated as hostile beyond the size cap.
- The occurrence check asks the server for two days around the occurrence; an occurrence moved further away is found by its override in the stored event.
- Nextcloud hides events marked `CLASS:PRIVATE` from a calendar's sharees altogether: the tools never see them, so an agent may book over a private appointment.
- Events with floating times are listed as if in the calendar's zone, while the server matches them against a range in its own (above); one near a range's edge may be missing or extra.
- A new `repeat` keeps the series' `EXDATE`s and changed occurrences, which may no longer fall on the new rule's days; calendar apps still show a changed occurrence where it is.
- sabre expands at most 3500 occurrences of one event per query, counted from its first: a daily series started about ten years before the range lists nothing, and Nextcloud only logs it.
- `calendar_conflict` covers a change made between a call's own read and its write, not one made between an agent's `list_events` and its write: an owner who moves an event on the phone in between gets the agent's change on top of theirs, computed from the old listing. The follow-up: `list_events` gives each event's version (its ETag) and the writers take an optional `expected_version`, sent as `If-Match` (independent review, 2026-11-14).
- Whether a deleted event can be restored depends on the server (Nextcloud keeps a trash bin; whether a sharee's deletes reach it is unchecked); `delete_event` says only that these tools cannot restore one.
- Without `CALDAV_CALENDARS`, the login's own calendars are listed beside the shared ones; `list_calendars` then says to ask the owner which to use. The tools cannot tell an agents' account from the person's own (on a generic server `DAV:owner` does not say which), so they do not mark the login's own calendars.
- A calendar named without its ` (owner)` matches any calendar so named: if the owner stops sharing "Patipa" and someone else shares a "Patipa" with the login, `CALDAV_CALENDARS=Patipa` picks theirs. Naming it by its id (`patipa_shared_by_<owner>`) avoids that.

## Tests

`tests/test_caldav_plugin.py` (with the shared session, the startup task, the kept calendar list and repeat rules), against `tests/_caldav_fake.py`, a stand-in CalDAV server shaped on Nextcloud (discovery, shared and read-only calendars, a task list, `expand` as sabre does it, ETags, 403 and 412), reached through `respx` so the plugin's own client runs unchanged. The registry tests (`test_issue_263_coverage_registry.py`, `test_issue_261_tool_admission.py`) and the connection-peak test count the plugin's tools.

Checked once by hand against a real server (2026-11-14, a throwaway `nextcloud:31-apache` container: an owner with one calendar shared read-write and one read-only with an agent user, events put in as DAVx⁵ writes them): discovery, the shared calendars' ids (`<uri>_shared_by_<owner>`) and names (`Patipa (admin)`), read-only rights from the privilege set, `expand` across the October clock change, percent-encoded object names, create, the duplicate guard, a read-only refusal, an occurrence moved and one deleted, a wrong occurrence refused, reminders and `X-` fields kept by an update, a stale `If-Match` refused (412), a series deleted, a wrong password (401). The fake's `expand` answers are shaped on what that server returned.

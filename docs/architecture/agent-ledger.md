# Agent ledger: what agents write for each other, in the database

> Read before touching the eight `ledger_*` tools, `src/services/ledger*.py`, `src/mcp_server/ledger_result.py`, the `ledger_*` tables or migration 032, `scripts/ledger_import.py` / `scripts/ledger_export.py`. The write tools are on the repo's mandatory-adversarial-review surface: they write primary data an agent acts on.

The agent ledger holds the logs agents keep for each other: **quirks** (Q: what Claude can or can't do on a surface, what works included), **feedback** (F: an unclear instruction, friction or a suggestion, from an agent or logged at the owner's request) and **proposals** (P: a change an agent proposed to an instruction for agents, and what went in). Eight MCP tools reach it; nothing else writes it. Fork-only (see `FORK.md`).

## The requirements this design answers to

Set by the owner (the design was reviewed with them on 2026-11-05); they outweigh any technical choice below.

1. **It is primary data.** Nothing in the vault rebuilds it, so it is backed up with the database, never re-derived. It is the first content in this database with that property (accounts and usage logs are the server's own bookkeeping).
2. **Real foreign keys and constraints wherever possible**, rather than IDs checked only by code: same-owner checks on every link between ledger rows; each kind's own fields as real columns with checks; the database itself refusing deletes and history rewrites. The one exception is links to the vault (an entry's or topic's area), so a reindex or prune can never reach the ledger.
3. **Nothing is ever lost.** No delete tool; every change states a reason and the revision it was based on, and is refused if the entry moved since; the previous version goes into an append-only history. Removing something for good (a sensitive detail logged by mistake) is the owner's act, from `psql`.
4. **Writes never wait for an embedding.** The reference server's Ollama is CPU-only and slow, and the claude.ai app drops a tool call after about 30 s.
5. **Two separate searches, never a merged ranking**: "by words" and "by meaning", side by side or one of them. When the provider is down, the meaning list says so and the words list still answers.
6. **The ledger and the vault stay apart**: `keyword_search` / `semantic_search` never return ledger entries, `ledger_search` never returns notes.
7. **What an agent needs goes in the tool descriptions first**, then the vault guide's primer (`vault_guide_primer.md`, "Agent ledger"), and only the rest in vault notes. Each description's first line stands on its own within about 80 characters; descriptions are generic (the repo is public). The read-only tools are marked read-only.
8. **Only feedback has `seen`** (the owner has heard of it), independent of its status. Every kind can be `superseded` or `retracted`. `dismissed` is the owner's alone — a convention in the tool description, since the server cannot tell the owner from an agent (every call carries the owner's credentials).

### What the database enforces

- **Owners.** Every foreign key between two ledger rows is composite over `(…_id, owner_key)` onto a `UNIQUE (id, owner_key)`. A composite key with a NULL column is not checked (MATCH SIMPLE), which is why it is not over `user_id`: in single-user mode every `user_id` is NULL and the check would silently not run. `owner_key` is never NULL, and user ids start at 1, so 0 is single-user mode's owner. The brief suggested keeping a plain key next to a composite one over `user_id`; the generated column makes the composite check total instead, so the plain key would add nothing (choice 1 below).
- **Kinds.** `ck_ledger_entries_status` allows each kind's own statuses plus `superseded` and `retracted`; one CHECK per group of kind fields says which kind must carry them and which may not (`ck_ledger_entries_quirk_fields`, `_feedback_fields`, `_proposal_fields`); `ck_ledger_entries_ref` ties the ref's letter to the kind and its digits to `number` (imported refs keep their zeros: `Q01` is number 1).
- **Lifecycle.** `superseded` ⇔ `superseded_by` (never itself); `handled` ⇔ `handled_account` and `handled_at`; an accepted or adjusted proposal has `final_text`; `seen` exists exactly for feedback and is true for feedback from the owner; feedback with an area is not `to_triage`.
- **Sizes.** Title 150 characters on one line, body 16,000, every other text column capped (CHECK or varchar). These caps are also what bounds `ledger_get`'s answer (L3).
- **No deletes, append-only history.** `ledger_refuse_change()` is a `BEFORE` trigger: `DELETE` on entries, topics, views, view columns and lines, ref counters and the history; `UPDATE` on the history; `TRUNCATE` on all of those and on the three link tables. Each raises `restrict_violation` naming the table — unless the session set **`SET LOCAL ledger.allow_delete = 'on'`** in the same transaction. That switch is the owner's way to remove something for good from `psql`; with it, deleting an entry cascades to its history, links, topic links, line sources and vectors (those keys are `ON DELETE CASCADE`), while an entry another one is superseded by, or a topic another was merged into, still refuses (no action). The link tables accept deletes: a tool removes a topic from an entry or replaces a line's sources, and writes a history row saying so.
- **No change without its history.** `ledger_require_history()` is a **deferred constraint trigger** (checked at commit) on entries, topics and view lines: any UPDATE that changes a row must raise its `revision` by exactly one, and `ledger_revisions` must hold a row for the old revision, whatever wrote it. Exempt: an entry's `seen`, `content_hash` and `embedded_hash` (they overwrite no content), and a session with the switch on. Deferred, so the order of the row's UPDATE and the history INSERT inside the transaction does not matter; but each row may be written **once per change**: the services run with autoflush off and flush once, after the bump (a premature flush would be an UPDATE without its bump, refused at commit).
- **One live line per matrix cell**: the partial unique index `uq_ledger_digest_lines_live_cell` on `(digest_id, row_label, column_label) WHERE removed_at IS NULL AND column_label IS NOT NULL`, since the rendered table shows one line per cell and a second would be hidden.
- **Users.** Every `user_id` references `users(id)` with no action, so the database refuses to delete a user who still has a ledger; the panel's permanent delete says so first (`users._has_ledger`). A test fixture that `TRUNCATE … CASCADE`s `users` reaches the ledger and must set the switch first.

### Migration 032 on a stamp-back rerun

Like 013 to 031, 032 is safe to re-run after `alembic stamp` back: it adopts the ledger already there, keeping every row, but only when **all** eleven tables and both trigger functions exist and the catalog matches 032 exactly — columns (types, defaults, generated expression), constraints, indexes, triggers, table markers and the functions' definitions. It finds out by building itself in a throwaway schema (`ledger_032_shape`) inside a savepoint, reading both catalogs with every name schema-qualified, and rolling the savepoint back. A partial set, a stray table of one of these names or a single altered object is refused, naming what differs: rows the server did not write would be served as agents' records.

What stays in code: the area check (areas live in the vault), the expected revision (compared under the row lock), reasons, the request-dependent limits.

### Locks

- An updated entry is locked **`FOR NO KEY UPDATE`**, and so are view lines being flagged: that mode does not conflict with the `KEY SHARE` lock every foreign-key insert takes on the row it cites, so citing an entry (a line's source, a related link) never deadlocks with updating it.
- The target of `superseded_by` is locked `FOR SHARE`, so it cannot be closed while it is being pointed to.
- Topics named in a write (`topics`, `topics_add`, `topics_remove`) are locked `FOR SHARE`; a merge locks both topics `FOR UPDATE`. A merge and a write naming the topic therefore run one after the other, and the write that waited reads the merged status and is refused, rather than linking an entry to a topic no search reaches.
- A deadlock, serialization failure or unavailable lock that remains (SQLSTATE 40P01, 40001, 55P03) is answered as `concurrent_write`: nothing written, read again and retry. Any other database fault is raised as itself.

## Entries

- **Refs.** A kind letter and the kind's own number (`Q84`, `F1`, `P1`), handed out by an upsert on `ledger_ref_counters` (row-locked for the transaction); a missing counter starts from the highest number in use. Lookups accept `q014` for `Q14`.
- **Add.** One transaction: the entry, its topics and links, review flags on `challenges`. Unknown areas, topics, fields or statuses are refused with the valid values in `allowed` (areas with their `description` from the main note's frontmatter). Feedback with no area is saved as `to_triage`, never refused. The answer carries up to five active entries sharing words with the title (`similar`, each with its area and topics): a word OR query over the same document the search uses; never a refusal. An entry saved with no area or no topics gets a note saying so, the topics its similar entries carry, the `ledger_update` call that adds them, and `areas_and_topics` (below). No similarity by meaning there, since the new entry has no vector yet and the write does not wait.
- **Superseding.** The target must be live (not itself superseded or retracted), and an entry that other entries are superseded by cannot be closed until they point elsewhere: no chain or loop can leave content in no active entry. Re-pointing a superseded entry is an ordinary change.
- **Update.** `ref`, `expected_revision`, `reason` are required (`stale_revision` with `current_revision` otherwise). The row is locked; `before` is a snapshot of every changeable field plus topics and related refs; the revision goes up by one; `content_hash` is recomputed. `append` adds `YYYY-MM-DD: text` as a new paragraph (the owner's local date, `TASKS_TIMEZONE`). Setting an area on `to_triage` feedback moves it to `open` (and clearing it, back), said in `notes`. Leaving `handled` clears the account; leaving `superseded` clears the pointer. An update that changes nothing is refused rather than recorded.
- **Seen.** `ledger_update(refs=[…], seen=true)` (up to 100) or a single `ref` with only `seen=true`: no reason, no revision bump, no history row — it can overwrite nothing. Non-feedback refs are listed as `not_feedback`, unknown ones as `not_found`.
- **Get.** Up to 20 refs; each with its fields, topics, related refs (both directions), the view lines citing it, feedback's citing tasks (`tasks`, `tasks_state`: see "Task links"), and with `history=true` every past version. The answer is kept within `MAX_READ_RESPONSE_CHARS`: later entries go to `not_returned`, the oldest history of an entry is left out with a note.

## What an agent needs, where it already is (ledger F34, owner's decision 2026-11-10)

On 2026-11-10 the voice relay was refused three times in a row by `ledger_add`, each refusal revealing one rule (the title's limit, `details.subtype`, `details.certainty`), though the docstring held all three; and none of its entries got topics, which only `ledger_topics` listed. The owner's principle: don't rely on agents doing steps in the right order; put what they need where they'll need it.

- **Every rule is in the parameter list.** `ledger_add` and `ledger_update` describe each parameter in the published schema (`Annotated[…, Field(description=…)]` in `server.py`), with the allowed values as `enum` and the caps as `maxLength`; `details` lists every kind's fields as properties, each saying its kind and whether it is required. These are added through `json_schema_extra`, which **describes without validating**: a wrong value still reaches the ledger's own refusal (with every problem, below) rather than a generic argument-validation error. The docstrings keep only what is not about one parameter.
- **One refusal names every problem.** `ledger.Problems` collects the refusals of every check that does not depend on a failed one (the status rules are skipped when the kind, the area, the origin or the details failed). One problem is refused exactly as before; several become one refusal whose message numbers them and whose `problems` lists each as `{field, code, message, allowed?}` (the code is theirs when shared, else `invalid_argument`). `details` is checked field by field the same way (an unknown field, a missing required one with its values, a wrong value). An update collects too, from its field checks on; `not_found` and `stale_revision` on the entry itself still refuse alone, since the caller must read the entry again anyway. A failed update may have half-changed the entry in the session: nothing is flushed (autoflush off) and the session closes without a commit.
- **The names are where agents are.** `ledger.names()` gives the area names (without `area/`) and the active topic names, one comma-separated line each. `ledger_search` returns them in every result (`areas_and_topics`: agents search before adding, to avoid a duplicate), `ledger_add` when the entry got no area or no topics, and `get_vault_guide` a section with each kind's required field, the topics with their descriptions and the area names. The guide's section is best-effort: without the database the guide answers without it.
- **Tested on agents before the push** (owner's request): six fresh agents with no context (three Haiku, three Sonnet), given only the published tool definitions and the real tools over a seeded throwaway database, each logged or updated entries from a realistic request (duplicates, an owner-reworded proposal, closing a fixed quirk, marking seen, an area with no fitting topic). None was refused and every new entry got an area and topics; what they misread became wording: areas with or without `area/`; what to do when no topic fits; quirk versus feedback for a behaviour the owner reports; certainty for the owner's own observation; `adjusted`; `origin` for every kind and on update; which status a quirk fixed upstream gets; that `append`, `status` and `seen` combine in one call; that `details` on update changes only the fields given; append, not a new entry, for the same thing seen again. Two were behaviour: a multi-word query found nothing unless one entry held every word, so `by_words` now falls back to entries sharing any word, best first, with a note; and the "matching entries have no vector" note counted the filtered entries, not the query's, and now says so. An add with no similar entry says so rather than returning nothing. A second round of three Haiku agents on the hardest cases found no refusal of the interface's making, and three more wordings: a kind's field passed beside `details` (`subtype=`) now gets a refusal saying where it goes instead of pydantic's bare unknown-argument error (a before-validator on the two tools' argument models, added where #295 swaps them); the no-topics note no longer urges a topic when none fits; `append` says the server dates the paragraph. Not changed: the test listed only six tools, so the guide's mentions of `ledger_digest` and `ledger_topic_edit` looked missing to the agents; on the real connector they are there.

## Search

`ledger_search` without a query lists by the filters, most recently changed first. With a query:

- **By words**: an exact ref match first (any status), then `to_tsvector(cfg, ref ‖ title ‖ body ‖ the kind's fields)` OR-ed over every `FTS_CONFIGS` entry, ranked by `ts_rank_cd`. **Computed at query time**, not stored (choice 3).
- **By meaning**: the query embedded with a timeout of `LEDGER_QUERY_EMBED_TIMEOUT_SECONDS` (20 s, under the ~30 s client drop), then exact cosine distance over `ledger_embeddings`, **ranked per entry in SQL** (its best chunk, `min(distance) GROUP BY entry_id`), joined to entries whose `embedded_hash = content_hash`. Ranking chunks and deduping afterwards let one long entry's many close chunks fill every slot. An outdated vector is never read; `not_embedded` counts the filtered entries without a current one, **in the same statement as the hits**: the background queue can commit a vector while the search waits on the provider for the query's, and a count read before that call once reported as unembedded an entry the meaning list held (found in the first live check). A provider failure or timeout fills `meaning_unavailable` and leaves the words list whole.
- Each list says when the other holds the same entry (`in_both_lists`). There is no merged ranking.
- Filters: kinds, area (or `none`), topics (all of them; a merged topic's name finds what moved to its target), status, origin, `unseen`, `since` (changed on or after the owner's local day), `tasks` (feedback by its task state, "Task links"; applied in SQL as a list of feedback numbers, so it reaches both lists; like every filter, it does not hold back the exact ref match a query for a ref puts first).
- Each feedback line carries its task state (`tasks`) when a task cites it.
- **`status="active"`** (the default) is quirks `current`, feedback `open` / `to_triage`, and **every proposal outcome**; `closed` is `stale`, `handled`, `dismissed`, `superseded`, `retracted` (choice 4).

## Vectors

- **The text** embedded and hashed is the title, body and the kind's longer fields (`ledger.embed_text`), chunked like a note.
- **After a write**, the tool hands the entry id to `ledger_embed.enqueue`, which never waits: one background task drains a deduplicated queue one entry at a time. The queue is bounded (`LEDGER_EMBED_QUEUE_MAX`, 200); past it, or while indexing is paused, the entry is left to the sweep, and the log says so.
- **The sweep** runs at the end of each scope's embed stage (`indexer._embed_vault_pinned`), after the notes and the exclusion reconciliation, with the **indexer's session factory** (so it reads and writes the database the stage does) and under the **same `EmbedBudget`**: it debits chunks, counts a note boundary per entry, stops on the budget or on the provider-failure streak, feeds the same streak, and records provider failures in the run row (`ledger entry F3: …`). So the ledger can neither hold the next index stage back nor hide an outage. It looks at up to 200 entries per stage, newest change first, **entries that failed at the provider before tried last** (in-process, like the notes' `_embed_failed_notes`), so a few entries the provider always rejects cannot stop the sweep at its head every pass; an input-too-large refusal does not count toward the outage streak. Embedded entries are not added to the run row's `notes_embedded` (that figure is about notes); they are logged.
- **Certification** mirrors the notes' (`embeddings._generation_matches`): the provider call runs with no transaction or lock open; then the generation lock, the stored fingerprint compared (match or absent), a conditional `UPDATE … SET embedded_hash = h WHERE id = … AND content_hash = h`, and only then the old vectors deleted and the new ones inserted. An entry edited during the call, or a reset or configuration change in between, writes nothing.
- **No vector index** on `ledger_embeddings` (choice 2).
- **Reset and startup.** `make reset-embeddings` and the panel's reset call `ledger_embed.reset_vectors` in their own locked transaction: delete every ledger vector, retype `ledger_embeddings.embedding` to the configured dimension, clear every `embedded_hash`. The stored fingerprint covers both tables, since both are certified under it. `_check_embedding_dim` checks both columns at startup.

## Summary views and topics

- **A view** is a list or a matrix of lines; a matrix's columns are rows of `ledger_digest_columns`, a cell is a line with a row and a column, one live line per cell. Each line cites entries; rendering shows the refs, a closed source's status (`Q5 stale`), and the date of the newest source (later of `observed_on` and the day it last changed); an unsourced line says so.
- **Flags.** Any entry update that changes something flags every live line citing it, `"<ref> changed: <reason>"`; `challenges` on add or update flags the named lines. A flag bumps the line's revision and writes a history row. The tool's answer lists the flagged lines so the agent that caused them deals with them then: `replace` (clears the flag) or `resolve` (it still holds), both with the line's expected revision.
- **Edits** are a list of operations applied all or none under one reason; a refusal names the operation. An operation with a key it does not know is refused (a misspelt `txt` would otherwise turn a `replace` into a silent `resolve`), and so is a `replace` that changes nothing. Moving a line into a taken cell is refused. `remove` sets `removed_at`; the row and its history stay.
- **Reading** a view is kept within `MAX_READ_RESPONSE_CHARS` (half of it with `with_ids`, where each line appears twice): the remaining lines, or rows of a matrix, are counted in `lines_not_shown`.
- **View hints.** A topic with at least `LEDGER_VIEW_HINT_MIN_QUIRKS` (15) current quirks, more than half of them cited by no live line, is named in `ledger_add`'s answer (for a quirk with that topic) and in `ledger_topics`.
- **Topics**: create (usable at once), describe, merge. A merge moves the entry–topic rows to the target and marks the source merged; the history row lists the entries that moved. The entries' own revisions do not change (choice 5). A merged topic is refused as an argument with the name of its target, and still works as a search filter.

## Task links

Feedback holds a problem and its `leads` (ideas for fixing it); what the owner decides to do becomes a vault task whose text cites the entry as **`ledger F12`**. That citation is the only link anyone writes: the server derives the other direction from the task index whenever a tool needs it (`src/services/ledger_tasks.py`). Owner's design (2026-11-09, proposal logged in the ledger): a hand-written back-link on the entry, and a rule that whoever completes the task closes the entry, both drifted (tasks ticked by hand in Obsidian never reach an agent), and `fix` read as a decision, so agents could not tell decided entries from open ideas.

- **The citation.** `ledger F<n>`, case-insensitive, whole words, spaces or tabs between the two (not other Unicode spaces), leading zeros ignored, one citation per entry (`ledger F9, F10` links F9 only). Only feedback refs count. PostgreSQL hands over the task lines holding the word (`ILIKE '%ledger%'`, a plain substring, so it can never leave out a line Python matches: a regex there follows the database's locale, where `\s` may not cover what Python's does; found by the adversarial review), then Python matches exactly.
- **Decided** means a task that is not cancelled cites the entry. **Task state** over the citing tasks, with statuses read as `list_tasks` reads them (the owner's Tasks settings, the global filter: a line the plugin would not read as a task does not count): `open` (one is not done or cancelled), `done` (all closed, one done), `cancelled` (all cancelled: undecided again). `NON_TASK` lines are ignored.
- **Where it shows.** `ledger_get`: `tasks` (each citing task's `path:line`, status type, text) and `tasks_state`. `ledger_search`: `tasks` on each feedback line, and the `tasks` filter. `create_task`, `edit_task`, `set_task_status`: `ledger_refs`, each cited entry with its title, status and task state, with the written note read from its text as published, the others from the index, so the state includes the write even when the immediate re-index could not run (an index pass holding the lock, a note not yet indexed: read from the index, a new open task beside an old done one came back as `done`, found by the adversarial review); the cited refs come from the written line, or the removed line's for a `🏁 delete` removal; a cited ref with no entry is `status: unknown`; a bare `F12` naming an existing feedback entry gets a note saying it links nothing. Reading the citations after a task write never fails the write: a failure there is a note.
- **`leads` is stored in the column `fix`.** The field was named `fix` until the owner's design above; tools, results, exports and new history versions say `leads`, older history versions keep `fix`. The column was not renamed because 032's stamp-back rerun adopts the ledger only when the catalog matches its own shape exactly: a renamed column would make every earlier migration's stamp-back rerun refuse at 032 (tried, and the schema gate's 22 rerun tests failed). The model maps the attribute to the column (`mapped_column("fix", …)`); the CHECKs name the column.
- **Nothing is stored.** No column, no foreign key into the index tables (requirement 2): a reindex or prune can change what the tools show, never the ledger.
- **What agents do with it** is in the connector's guide (ledger section): create the task with the citation once the owner decides; close an open entry whose tasks are all done as `handled`; an entry whose tasks were all cancelled stays open, undecided.

## Rate control and the write budget

The four writers (`ledger_add`, `ledger_update`, `ledger_digest_edit`, `ledger_topic_edit`) carry `write_class=True`, so they draw on the per-principal write bucket like the vault writers, and are concurrency class `write`. `ledger_search` is class `embedding` (its default mode embeds the query), `ledger_get`, `ledger_digest`, `ledger_topics` are `light`. `CLASS_MAPPING_VERSION` is 4. In code `write_class` only ever selected the bucket; its docstring and `rate-limits.md` used to define it as "changes vault bytes", which the ledger writers do not. The meaning is now "charged to the write budget", and the docs list the two groups (choice 6).

## Import and export

`scripts/ledger_import.py FILE (--user NAME | --single-user) [--dry-run] [--skip-area-check]` reads one JSON file (format in its docstring) and imports it in **one transaction**, keeping refs, dates and statuses, setting the counters, inserting each superseded entry after its replacement (the CHECK is immediate), and refusing any clash rather than merging. `--dry-run` writes everything then rolls back: the rehearsal check. Areas are checked against the indexed vault unless `--skip-area-check`. Entries land unembedded; the sweep embeds them over the next passes. `scripts/ledger_export.py` writes Markdown (optionally with history) or the import's JSON, from one read-only repeatable-read snapshot; the JSON carries review flags, not the history, removed lines or merged topics. Both read only the server's own configuration (`DATABASE_URL`), so they run in the app container, a one-off job or any shell with it set; neither assumes a deploy path. The data never enters the repository.

## Choices made by the agent that built this (not requirements)

Recorded so they are never mistaken for the owner's rules; each can be changed.

1. **`owner_key` instead of a plain foreign key beside a composite one** (above).
2. **No vector index on `ledger_embeddings`.** The proposal suggested the vault's half-precision index. At the ledger's size (hundreds to a few thousand chunks) an exact scan is fast and cannot miss a candidate that a filter discards, which HNSW can; it also keeps the index out of `include_object` and the reset. Add one through `vector_index` if the ledger outgrows ~50,000 chunks.
3. **The words document is computed at query time**, not stored as a tsvector: a stored one goes stale silently when `FTS_CONFIGS` changes (the notes need `make rebuild-tsvectors` for that), and at the ledger's size the parse is cheap.
4. **Every proposal outcome is "active".** A proposal's outcome is its record, and the "was this already tried?" check needs rejected ones by default; only `superseded` / `retracted` proposals leave the default searches.
5. **A topic merge does not bump the entries' revisions**, so it cannot make every agent's next update of those entries stale; the merge is recorded on the topic.
6. **`write_class` keeps its name** and now means "charged to the write budget"; the brief asked to split a flag that, in code, had only ever meant that.
7. **`expected_revision` is optional for topic edits**, required for entry updates and for view-line replace / remove / resolve. Creating a view or a topic, or adding a line, has no prior version to name.
8. **`seen` changes neither the revision nor the history.**
9. **`created_by`** is `api_key:<name>` or `oauth:<client name>` from the credential; `author` is the agent's own optional name. Imports default to `import`.
10. **Destructive markers.** The four writers are marked `destructiveHint=False` (nothing they do is lost), the four readers `readOnlyHint=True`. The other connector tools still carry none (design note, "Later").

## Accepted limitations

| # | What | Why accepted |
| --- | --- | --- |
| L1 | Owner-only conventions (`dismissed`, topics and views told to the owner) are not enforced. | The server cannot tell the owner from an agent: every call carries the owner's credentials (design). |
| L2 | A new or changed entry is found by meaning only after its vector lands (seconds to a pass later; longer when the provider is down). | Requirement 4; `not_embedded` says how many, and the words list covers them. |
| L3 | One entry can make a `ledger_get` answer exceed `MAX_READ_RESPONSE_CHARS` (its fields' caps sum to about 70,000 characters). | Bounded by the column CHECKs; splitting one entry would hide part of a record. Several entries never exceed the cap together. |
| L4 | The background queue is in-process: a restart loses it. | The sweep re-finds every entry whose vector is missing or outdated. |
| L5 | An area that is no longer declared (main note renamed or deleted) stays on its entries; `ledger_topics` lists it under `areas_no_longer_declared`. | Links to the vault are deliberately not keys (requirement 2); a re-declared area picks the entries back up. |
| L6 | Similar entries on add are by words only. | The write must not wait for an embedding. |
| L7 | The owner's switch can also rewrite the history (`UPDATE` with the switch on). | It is the documented way to remove a sensitive detail for good, and only a direct database session can set it. |
| L8 | Topic edits take an optional `expected_revision`, and a view's own title and description none: the last write wins there. | The history keeps the previous version with its reason; these are rare, low-stakes changes (choice 7). Found by the adversarial review, declined. |
| L9 | `make reset-embeddings` and the panel's reset hold every entry's row lock and an exclusive lock on `ledger_embeddings` until they commit, so ledger writes and meaning searches wait for them (up to the statement timeout). | A reset is a rare maintenance step taken with the indexer paused. Found by the adversarial review, declined. |
| L10 | Task links read the task index, which lags behind hand edits in Obsidian until the next index pass. | The task tools re-index their note at once; a pass is minutes away. Checking every citing line on disk would read many notes per ledger call. |
| L11 | A task with `🏁 delete` disappears when done, and its citation with it: the entry reads as undecided again. A deleted note or task line breaks the link the same way, silently. | Only the citation links; `set_task_status` reports the removed line's citations, which covers an agent ticking it. Avoid `🏁 delete` on a task citing an entry. |
| L12 | A citation in a form other than `ledger F12` (a bare `F12`, `ledger #F12`) links nothing. | One fixed form keeps matching exact; the task tools point out a bare ref that names an existing entry, and echo every link they find. |

## Adversarial review (2026-11-05)

A separate agent attacked the write tools, the schema, the embedding path and the scripts with probes against real Postgres. Nothing it found lost data, let a delete through, or crossed owners. Fixed: a no-op update crashing instead of being refused, and re-pointing `superseded_by` or changing a handled account read as no change; two live lines in one matrix cell (now a unique index); the meaning list ranked by chunk (now per entry); a topic merge racing a write; failing entries stalling the sweep; deadlocks surfacing as internal errors; superseding loops and closed targets; misspelt operation keys; no database guarantee of history on update (now the deferred trigger); no cap on `ledger_digest`; the export's snapshot and review flags; an unconditional hash re-stamp. Declined: L8, L9.

## Refusal codes added

`stale_revision` (`BODY_CODES`), with `current_revision` in the result. The rest are the repo's codes: `concurrent_write` (a lock conflict; retry), `invalid_argument` (with `allowed` when a value was unknown, and `problems` when there were several), `not_found`, `already_exists`, `size_limit`, `permission_denied`, `validation_failed` (a constraint the database refused).

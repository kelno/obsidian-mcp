# Agent paths: `agent_path` and `agent_path_reached_by`

> Read before touching `src/plugins/kelno_vault/agent_paths.py` (the engine), `agent_path_tools.py` (the two tools) or `agent_path_result.py` (their results). Fork-only (see `FORK.md`), tools of the `kelno_vault` plugin, served only with it loaded ([plugins](plugins.md)).

The fork owner's vault holds the rules its agents follow, spread over notes, `## For agents` sections, hooks on the owner's PCs, Claude's memory and this server's own tool texts. Which of them a given agent actually meets, and in what order, was written by hand and drifted. These two tools draw it from the setup as it is, so an agent changing a rule can see who meets it and what is around it (owner's design, 2026-11-18; the vault note `Areas/Agent personnel/Agent paths/Agent paths - path tool.md` holds the design and the owner's decisions):

- `agent_path(start, work, known)`, forward: "I'm this agent, doing this work: what do I meet?"
- `agent_path_reached_by(place, known, machine)`, backward: "this rule lives here, or would: who meets it, and what's around it?"

Both read-only, admission class `scan` (each call reads the vault's rule notes; adding them moved `TOOL_CLASSES`, so `CLASS_MAPPING_VERSION` is 9).

## Where it comes from

The tools were first built as a script on the owner's PC (`agent_paths.py` in a plain folder, its prototype). The owner moved them here (2026-11-18): a claude.ai chat cannot run a script on the PC, and only this server has its tool texts as served. The engine is that script's reading rules, ported line for line, with its input swapped; its pieces, ids and hashes are the prototype's, so the two can be compared. On 2026-11-18, run on the real vault with the fixture's tool texts, it gave the same pieces (ids, hashes, stages, moments, order), the same structural facts and the same unreached rule files as the prototype's `typical` for all five typical agents. Change a reading rule here, not there: the prototype is no longer maintained.

## What it reads

The tool wrapper (`agent_path_tools.py`) gathers four inputs; the engine (`agent_paths.py`) imports nothing from the server, so it also loads on its own.

1. **The vault**, through the caller's root: every visible file (hidden folders and files left out, as the file tools do), each read with `read_bytes` (`MAX_NOTE_BYTES`) and decoded as Python's universal newlines read it on a PC (`CRLF` and lone `CR` become `LF`), so hashes match the PC's. From it: the rule-file definition (`rule_files`, `_/Rule files.md`; unreadable is a refusal, since without it no pointer can be told from a mention), the list of areas (`areas_index`, `Areas/Areas.md`; unreadable is a note), Claude's memory through its mirror note (`MEMORY_NOTE`). (The engine can still read the hand-written paths, `WHERE_NOTE`'s `HANDWRITTEN_HEADING`, as the prototype did; the tools no longer show them: ledger P251 replaces that list with these tools.)
2. **The starting points**, `STARTING_POINTS_PATH` (`_/agent-paths/starting-points.toml`), the only hand-written input: what each surface loads first (a fact of the product no file states: claude.ai starts from memory; Claude Code loads `~/.claude/CLAUDE.md`, the folder's `CLAUDE.md` files, then its session-start hooks) and the five typical agents, each a surface, a folder, who started it and a role, numbered as in the hand-written list. It lives in the vault, not here, because it names folders on the owner's PC, and this repo is public (AI suggestion). Since ledger P251 it is the reference for the loading order: `WHERE_NOTE`'s "Loaded at the start" points to it, and a new kind of agent is added there. Unreadable is a refusal.
3. **The PC side**, `SNAPSHOT_FOLDER/<machine>.json` (`_/agent-paths/`): what only a PC sees, written by a session-start hook on each PC (the vault's `_/claude-code-hooks/agent-paths-snapshot.py`) in the background, rewritten only when its content changed, carried here by the vault's sync. Formats 1 and 2 (`SNAPSHOT_FORMATS`; another format is left out with a note): `machine`, `made` (when the PC side last changed), `vault` and `home` (where they are on that PC), `folders` (for the vault, the home folder and each related folder of the list of areas that exists on that PC: `loads`, the files Claude Code loads at the start in order, each `note:<vault path>` or `file:<PC path>` with how it arrives, imports included; `session_start`, each session-start hook's message on a sample start there, with its hash), `files` (the text of each `file:`), `hooks` (every hook registered, by event and matcher), `relay_notes` and `relay_config`; format 2 adds `hook_scripts`, each registered hook script's id (`note:<vault path>` or `file:<path>`) and the digest of its file as the snapshot ran it, and two optional keys that don't change the format: `hook_messages` (what every hook other than the sampled session-start ones says, by `hook:<event>/<script>`: `{event, matcher, messages: [{when, text, hash}]}`, `messages` null with a `why` when the script can't say them; each script reports its own through a `messages` role, ledger P263), and `bridge` (the voice bridge's own texts from its `claude-voice texts` command: `{command, instructions, guide, tools: [{name, text, hash}], notes: [{when, text, hash}]}`; null when the bridge isn't on that PC, `{command, error}` when the command failed). A hook script is a vault file, read live here: when one on the path differs from that digest, the result says its message may be out of date, and how to refresh it (`agent-paths-snapshot.py run` from a Claude Code session on that PC; from claude.ai, ask the owner or a desk session). Owner, 2026-11-18: the tool says when the snapshot is out of date and what to do, instead of a rule teaching it. On the PC the hook also refreshes the snapshot after an edit to its inputs and after a git command that can change a checkout, so this mostly covers edits made from claude.ai; the repo files the server can't see (`file:` pieces) have no such check. Several PCs: `start.machine` / `machine` picks one; without it the most recent `made`, with a note. A start folder the snapshot does not hold uses the deepest folder above it that it does, said under `not_followed`; with none above it, what loads in every folder (the user `CLAUDE.md`, its imports, the user rules) comes from the home folder's entry, and its own `CLAUDE.md` files and what the session-start hooks say there are said unknown under `not_followed` (test bench, 2026-11-19: such a start got nothing at all). No snapshot: the Claude Code side is said to be missing, never guessed.
4. **This server's texts as served**: `tools/list` unscoped (`FastMCP.list_tools`, the full list whatever the caller's credential, since a path is about a kind of agent), each tool's description followed by each top-level parameter's description, every loaded plugin's lines included; the server instructions; the server's part of `get_vault_guide` (`tools.vault_guide_server_part`, the one function both use, so the guide is hashed exactly as served); `open_area`'s instruction lines (`OPEN_AREA_INSTRUCTIONS`).

## Pieces

Each piece has an id naming what it is: `note:<vault path>`, `section:<note path>#<heading>`, `file:<PC path>` (a file outside the vault Claude Code loads), `open_area:<main note path>` (an area's main note as `open_area` serves it, without its For agents and Tasks sections: not the note's text, so not its id, which a caller holding the whole note's hash would take for it; test bench, 2026-11-19), `hook:<event>/<script>` (a session-start hook's message) and `hook:<event>/<script>#<n>` (its n-th message at another event), `hook:<event>/<script>`, `memory:/preferences.md` and `memory:/profile.md`, `tool:obsidian-mcp:<tool>`, the voice bridge's `instructions:claude-voice`, `guide:claude-voice`, `tool:claude-voice:<tool>` and `bridge:claude-voice#<n>` (its n-th note under relayed messages), and three this server adds beyond the prototype: `instructions:obsidian-mcp`, `guide:obsidian-mcp` and `tool:obsidian-mcp:open_area/instructions` (AI suggestion). Its hash is the first 12 hex digits of its text's sha256, the PC hook's own digest; the hash only assures nothing changed (owner).

A piece's `stage` orders the path, by when it reaches the agent: loaded at the start, session-start hook, read at the start, at the first bridge result, when the work's area is opened, when the connector's tools load, when its moment comes (test bench, 2026-11-20: the tools came last, after every moment piece, as if met last; they load with the session, and a moment comes later in the conversation). Within a stage, pieces that arrive whatever the conversation brings come before those waiting on a moment, and a pointer that says when before one that doesn't; then the order they were met. The start's pieces are taken in first, then the area's, then what the hooks say at other events, then the tools; the path is shown in stage order, stable within a stage (test bench, 2026-11-19: the area's pieces came after the moment pieces).

**Every way a piece arrives is kept, none picked as its route** (owner, 2026-11-19: "Yes with option 1"; until then the first arrival won, and the others were bare ids in `also_pointed_by`). Each arrival is a moment, the piece holding the line, and the line (`Piece.arrivals`). The earliest certain one places the piece (its `stage`, `always`, `arrives`, and the chain `agent_path_reached_by` shows): one on the path whatever the conversation brings beats one waiting on a moment, then the earlier stage; a piece placed again that way is followed again, so what it points to is placed the same way. So an area's `## For agents`, met first behind "Before filing a note into a folder", arrives at the area's opening (test bench, 2026-11-19: it stayed a waiting piece, and `agent_path_reached_by` missed Mail's open_area chain). Its `moments` (`PathBuilder.moments_of`) are every moment that leads to it, in the order the agent meets them, each with the pointing piece and its line. A pointer that holds from when it is met ("when met", "At the start", "While…") in a piece that itself waits on a moment leads to its target only when that piece is read: its moments are that piece's, with the pieces between in `through` (test bench, 2026-11-19: the Relay note's "At the start" showed alone, on a plain chat). Any other pointer's moment is its own. An arrival no line brings gives its moment when it has one (a hook's message, a nested `CLAUDE.md`), nothing otherwise (what loads at the start), except what `open_area` serves: "when the area is opened", from `tool:obsidian-mcp:open_area` (test bench, 2026-11-20: an area's `## For agents` showed only another route). **The arrival that places the piece comes first, marked `placed`** (`PathBuilder.placing_first`); the others are other routes to it, some on other agents' paths (cold read, 2026-11-20: listed flat, they seemed to contradict `always` and `stage`). **A line in a piece that itself waits on a moment says after which** (`after`, that piece's placing moment; `PathBuilder.with_after`): Agent personnel's "When working in this area" read as a route to coding-practices on every area's path, when that section arrives only "Before filing a note into a folder" (test bench, 2026-11-20).

**A moment that doesn't stand alone comes with its whole line** (owner, same decision), so it reads right out of context. `agent_paths.stands_alone` decides it on words: a moment holding a word that points back into its line (`it`, `its`, `this`, `these`, `those`, `there`, `here`, `that` ending a clause, `such` but not "such as", `one` but not "one of") doesn't stand alone ("When choosing it", "When working in this area", "When starting one"). They, them and their are left out: in the vault they are the owner's pronouns ("about their areas"). Only the moment's own clause counts: what is in parentheses or quotes, and what follows a colon or semicolon (a guide index's "when to read it" may go on: "…: it starts with an upstream check"), is left out. A word caught wrongly costs only a line shown whole; a noun naming what the line is about ("When the area is new") isn't caught, an accepted limit. Any other line is cut around its pointer (`agent_path_tools._window`): from the start of the sentence holding the moment, past the link, about 240 characters, a link far beyond coming after " … " with a little around it (test bench, 2026-11-20: cut from the line's start, 7 of 45 lines lost the moment or the link).

**A moment is the pointer's whole condition** (`agent_paths.whole_condition`): from its opening up to where its instruction starts (", read …", ": read …", ", follow …", and a few other verbs), within its first sentence, so "Before working on one of the owner's areas, or writing or changing anything in the vault", not only its first phrase (cold read, 2026-11-20: the half cut off was the one that applied). With no instruction verb in that sentence, or a cut inside a parenthesis, the moment stays its opening up to the first comma, colon, semicolon, full stop or table cell. On the owner's vault, 9 moments grew this way.

## Reading rules (from the prototype)

- **What loads by itself**: on Claude Code, the snapshot's top-level loads for the folder, in the steps `starting-points.toml` names: the user `CLAUDE.md` (`user_claude_md`; an entry the snapshot marks `exists: false` loads nothing), the files of `~/.claude/rules/` (`user_rules`), the folder's `CLAUDE.md` files and its own rules folder (`folder_claude_md`), then the `@` imports of each loaded `.md`, followed recursively (resolved as Claude Code does: `~` is the PC's home, a relative path is against the importing file). Only what Claude Code loads expands imports. A folder below the start folder that the snapshot holds (a repo inside a related folder, `claude-voice` under `voice-bridge`) has its own `CLAUDE.md` files loaded when the session reads a file there, not at the start: each is a piece waiting on "when it reads a file in <folder>", its imports expanded with the same moment (test bench, 2026-11-19: they were on no path). A start in a worktree, `<repo>/.claude/worktrees/<name>`, loads the worktree's own `CLAUDE.md` files and not those of the folders above it (Q134; the PC snapshot's rule): the repo's own as its main checkout has them (the snapshot holds no worktree), said under `not_followed` (test bench, 2026-11-19: a fork worker in its worktree got the parent folder's `CLAUDE.md`). An import the snapshot lists in the folder's `skipped_imports` (in a project's file, one outside the session's folder, which Claude Code holds for an approval the desktop app never asks for; the user `CLAUDE.md` is exempt) is not loaded: it shows in `structure.skipped_imports`. An imported file whose snapshot entry carries a `warning` (its import line sits next to another import, which made both fail to load in some tests, Q134) stays on the path, as the snapshot lists it loaded: its `arrives` ends with "(may not load: …)", and the warning shows in `structure.import_warnings`. Taking it off the path would claim more than the tests show (`@./rel.md` loads next to other imports).
- **Hooks**: the session-start messages of the folder's snapshot entry; a hook that prints nothing puts nothing on the path. The hooks are the user's, so they run in every folder: in a folder the snapshot doesn't hold (one no area lists, a worktree), a held folder of the same kind stands for it (`hook_source`: the vault for a folder in it, else the deepest held folder above it outside the vault and the home folder, else the first such), its message taken as what it says in the home folder followed by what it adds in that folder, with that folder's path replaced by this one's in the added part only (the machine's rules may name a folder too); the area-start hook's message differs between such folders by the path alone, and `arrives` says where it was taken from (test bench, 2026-11-19: a start in an unlisted folder got no hook, so no role note). On every Claude Code path, each message of `hook_messages` is a piece too, `hook:<event>/<script>#<n>`, waiting on its `when` as its moment (named by its position in the script's list, so a script adds a new message at the end, as the vault's "Where agent instructions go" says, or the later ones show as changed to a caller holding their hashes); like a tool's text it isn't a rule file, so what it points to isn't followed (ledger P263). A script whose `messages` is null is listed under `not_followed` with its `why`; a snapshot without the key keeps the old line, "hook messages at other events". A line naming several role notes (`_/agent/roles/`) keeps only the start's role note; without a role, each waits on its role (moment "if its role is <name>"), with a note to pass one (test bench, 2026-11-19: both came as read at the start). A message saying the lines after it are a note's rule section ("from the `## For agents` section of <note>:", the area hook's machine rules) brings that section with the message, at the start, `arrives` "copied into <hook>'s message", ending "(the copy differs from the section now)" when the section's lines aren't all in the message (test bench, 2026-11-19: it showed only behind its later pointer).
- **Pointers in rule files**: wikilinks, backticked vault paths ending `.md` and absolute paths ending `.md`, each with the sentence holding it; a wikilink inside inline code or a fenced block is code (an example), not a link. Between rule notes, a link is a pointer only in one of a closed list of shapes, which the vault states in "How to write an instruction" in `WHERE_NOTE` and every rule follows (owner, ledger P250, P259): its bullet or sentence opens with **At the start**, **While**, **When** or **Before**, the first word counting and anything before it that isn't a letter ignored (so a bold label in front doesn't pass), or it takes the guide index's shape (`- [[guide]]: when to read it`, for the line's leading link only; a backticked path or a Markdown link leading the line is its link too). A bold title that is a sentence of its own (`**Landing.** When you merge, read …`) ends there, so the next sentence's opening counts; a bold label that isn't (`**Roles**: when …`) is the opening, and doesn't pass. The tool reads exactly that list and guesses no other form (owner): any other link from a rule note or memory's lines to a rule file, or to a rule section by its heading (`[[Areas/X/X#For agents]]`), a plain "read X" included, is a mention, listed in `rule_file_mentions` and not put on the path. A pointer's moment is that opening up to the first `:`, `;`, `,`, full stop or table cell (` | `), or the index's "when to read it". Text not written under the convention (a hook's message, a main note's text) keeps a reading verb aimed at the link as a pointer, moment `when met`; a link there that says neither is `unplaced`. "At the start" and "While…" hold from the moment the pointer is met; any other moment makes the piece wait on it. A link to another note with no reading verb is a mention too, counted, not followed; read, such a note is followed for its rule sections only. A backticked vault path holding `<placeholder>` segments names a kind of note (ledger P261, P262: "the `## For agents` section of its folder note, `<folder>/<folder>.md`", "its note, `Reference/Servers/<name>/<name>.md`"): every vault note matching it is reached, with the line's moment, as if the line pointed to each. A placeholder stands for one folder or file name, the same name where it repeats; one opening the path stands for any folder, its last name being the one a repeat compares with, so `<folder>/<folder>.md` is every folder note at any depth. When the sentence names a rule section in backticks (`## For agents`), each match's section is the piece and only notes that have one count; otherwise a match is taken as the same line pointing to it would be. Such a line is a pattern, not a pointer, unless it says when (the convention's shapes between rule notes) or, to a note that isn't a rule file, "read"; a line that brings nothing is one mention, not one per match. Paths opening with `~`, `/` or a drive, and imports (`@<vault path>/…`), are not patterns. (AI suggestion: the reading of a leading placeholder; the owner's brief named the two patterns.)
- **In a repo, the tools stop at what Claude Code loads** (owner, 2026-11-19, ledger P277): a file outside the vault (a repo's `CLAUDE.md`) has its imports expanded as above, and beyond them only its links into the vault are followed. A backticked `.md` path or a Markdown link to a `.md` file (not a URL, not a placeholder, not a command such as `git show main:CLAUDE.md`, not in a fenced block), resolved against the pointing file's folder, then the session folder's root, that lands in the vault is a vault pointer, read by the vault's pointer shapes (the index's link may be a Markdown link or a backticked path there). A link to anything else, such as the repo's own docs, is left, neither a piece nor a mention: an agent reads those docs by hand with the repo's files in front of it. Every path's `not_followed` says so, with the rest of what the tools leave out by design: the paragraph opening "The tools don't follow, by design:" (`BY_DESIGN_OPENING`) in `WHERE_NOTE`'s section "Checking a rule against agent paths", read at each call, so the list has one home; without that paragraph the entry says it is missing.
- **The work's area**: `work.area` takes what `open_area` takes: the area's name, its main note's name, a related folder, or its slug or tag (`area_tag`, as `chronic-symptoms`, `area/…` or `#area/…`; only a slug or a tag reads the main notes, so a folder's runs aren't tied to every main note). What `open_area` serves, rebuilt from the files: the main note's `## For agents` section, the main note without that section and its Tasks section (its links followed to rule files only, and reported when they are), Vault conventions' "Working on an area", coding-practices when the main note sets `code_project: true`, and `open_area`'s instruction lines as served. A main note without a `## For agents` section says so under `not_followed`, so a reader tells it from a section left out (test bench, 2026-11-20). A Claude Code session in a folder an area lists gets that area without `work`.
- **Tool texts**: the server's texts as served, at their stage, after the area's pieces and before the moments. The guide (`guide:obsidian-mcp`) is on every path, not waiting on a call: every agent on the connector calls `get_vault_guide` first, as the server's instructions and the tool's first line say (the fork's decision "Agents read the guide"); its `arrives` says so. The vault note it returns after its own part (`VAULT_GUIDE_NOTE`, `ServedTexts.guide_note`) comes with it, on the path as the guide is, its moment "when get_vault_guide is called" from `tool:obsidian-mcp:get_vault_guide` (test bench, 2026-11-19: the guide was always while Vault conventions, in the same result, waited on a moment). It counts as the vault note it is, not as a tool text (`agent_paths.tool_text`), in the sizes and the overview. So Vault conventions is on every connector path whatever the conversation brings.
- **Memory's mirror**: `MEMORY_NOTE`'s `## Lines` and `## Profile` are Claude's memory as claude.ai loads it (the `memory:` pieces). Read as a note, on any surface, their links aren't followed: they instruct a claude.ai chat, not whoever reads the mirror (test bench, 2026-11-19: they put the list of areas and the Spice test on Claude Code paths).
- **The voice bridge's texts** (snapshot's `bridge`), for an agent on the bridge: the relay (a claude.ai start with the relay's notes) gets the instructions and tools when the bridge's tools load and the guide with its first bridge result, at the bridge stage; a Claude Code session on the bridge (the Coordinator, by its role, and a session started by the relay or the Coordinator) gets the instructions and tools when they load and the guide when it first calls the bridge, waiting on that moment, and each note at its `when`. None is a rule file: their links aren't followed. A failed command, or no bridge on the PC, is said under `not_followed`; a snapshot without the key keeps the old line. Every claude.ai chat has the bridge among its account's connectors (memory's lines tell a chat how to use it): its tool texts when they load, its guide waiting on its first call, as for a Claude Code session on the bridge, and no notes (test bench, 2026-11-19: the guide memory points to was on no chat's path). Who is on the bridge follows the brief of the Agent paths session (2026-11-19). The overview folds each server's tool texts into one line.

## Results

- `pieces`: each with `id`, `stage`, `arrives` (how it arrives first, in words), `always`, `where`, `chars`, `hash`, `moments` (each `{moment, piece, line, through, placed, after}`: the line whole when its moment doesn't stand alone, else the part around the pointer; the placing arrival first); with `known`, `status` (`new`, `changed`, `unchanged`), and `text` only for new or changed pieces. Without `known` every text comes. On a first call (no `known`) every piece is listed, one whose text comes in a later call (`text_withheld`) in **short form** (`id`, `stage`, `always`, `moments` without their lines, `hash`), its details coming with its text: the short form stays short (owner), but a moment that doesn't stand alone keeps its line there too, rare enough to cost little, and the note on withheld texts says so. A call with `known` lists only what it brings: the pieces with their text this time, those now marked in parts, new private ones; the pieces held and those still waiting were in the first call, so they are left out, counted in `waiting` (on a first call, `waiting` counts the `text_withheld` ones), and a removal shows in `left_path` (owner, 2026-11-18: repeating them took most of each call on a backward question, one or two texts per call). A piece that joins the path between calls arrives whole when its turn comes. The `structure` and a backward question's `reached_by` are left out of such a call too (owner, 2026-11-18: 9,000 characters a call on a backward question); a call without `known` shows them, and the note says to make one when the caller hasn't had them (a first call with `known` drops them too).
- **The size budget**: a first call's texts run past 100,000 characters on most paths (the tool texts alone are over 100,000), and the details of a backward question's 150 pieces alone reached 50,000 on the owner's vault. Every result is held to `PAGE_CHARS` (80,000), 1,000 kept for notes: twice the server's read cap (`MAX_READ_RESPONSE_CHARS`, 40,000, which every other tool keeps), on trial since 2026-11-18 (owner), since at 40,000 reading a whole path took 12 to 20 calls. Claude Code refuses to show a model a connector result past `MAX_MCP_OUTPUT_TOKENS` (25,000 tokens by default; this JSON, hashes and paths, runs about 2.3 characters a token, so a 59,000-character result was refused and saved to a file): the owner's PCs set it to 50,000 in Claude Code's settings (New PC setup). Claude Code also saves to a file, whatever its tokens, any result past 50,000 characters unless the tool's `tools/list` entry declares `_meta["anthropic/maxResultSizeChars"]` (live check 3 found 75,000 to 79,000-character results saved to a file with the token limit raised): both tools declare 100,000, through the plugin tool's `meta`. A PC without the setting gets a page past about 59,000 characters as a file to read. The first live call (2026-11-18) found it wasn't: the overview was 222,000 characters (each agent's `rule_file_mentions` quoted 60-odd whole lines) and a backward question 59,000, every text wrongly marked in parts; hence the shape below. Texts are filled in path order while they fit, except that once a rule piece on the path whatever the conversation brings waits for a later call, no piece waiting on a moment after it comes first (test bench, 2026-11-20: a page sent moment pieces while an always one waited, so a reader paging through met them out of order); the tool texts are filled after every rule piece, wherever the tools load on the path (listed before the moments, over 100,000 characters, they would otherwise push every moment piece past the first pages) (by an estimate, then the whole result measured and the last texts taken back until it fits); the rest are marked `text_withheld`, in short form, with a note to call again passing as `known` the hashes of the pieces whose text the caller now holds; those withheld are then new, and come next: `known` is the mechanism the design already gives (AI suggestion). Every call makes progress, so a caller doing that gets every text in a bounded number of calls: the first text due either arrives or is marked `text_in_parts`. A text larger than the room it would have (on a large path, a 30,000-character note; the obsidian-mcp repo's own `CLAUDE.md` was 82,000 characters until its cut on 2026-11-18) is marked `text_in_parts` (promising it "next" could send the caller round forever) and comes in parts (owner, 2026-11-18, so a claude.ai chat, which can't read a PC file, gets it too): a call with the same arguments plus `read_from: {id, offset}` returns that piece alone, its text from `offset` as far as the budget allows (often whole in one part), with `text_offset` and `next_offset` (none after the last part); the hash is the whole text's. Past the budget even in short form (some 400 pieces), the last pieces waiting for their text are left out and the structure's lists cut short (`cut`), said in the notes. The overview is bounded the same way: structure lists cut from the last typical agent back, then piece lines, a cut path ending on how many it leaves out.
- **The tool texts are short on purpose** (owner, 2026-11-18): the descriptions and parameter texts say only what an agent needs to call the tool, and the result models carry comments, not docstrings, since a model's docstring is sent with the tool's schema. How to read a result comes from the result itself, its fields' words and its notes (what a withheld text or one in parts needs), and from one line of `agent_path`'s description: `structure` lists facts to judge, not faults. This note is the field reference, linked from that description for maintaining the tools only: nothing an agent needs to use a result lives only here, checked with cold readers given the descriptions and a sample result alone (owner, 2026-11-19; until then a paragraph in the vault's `_/agent/Where agent instructions go.md` explained a result, and drifted).
- `left_path`: with `known`, the held pieces no longer on the path, so a caller comparing against its hashes sees a removal, which no status can show (found by the cold reader, 2026-11-18).
- **Private notes**: a piece in a private folder (`PRIVATE_FOLDER_NAMES`) is marked `private` and never carries its text (P98).
- `structure`: facts, never judgments (owner): `size` (characters and pieces always on, waiting on a moment, and tool texts), `unplaced_pointers`, `pointers_outside_rule_files`, `into_areas` (one entry per piece reached and kind, `{to, kind, from: [...]}`, since one pointer copied into 26 area main notes took 26 entries, half a first page (test bench, 2026-11-20); shared into local, or local into another local: a shared piece is met by every agent of a kind, a local one only by agents working in that area, folder, machine or repo; owner, ledger P276, keeping "trunk" for its sense in Common-rules), `mentions_not_followed` (a count), `mentions` (on one agent's path only, those to notes that aren't rule files, one entry per note, `{target, from: [...]}`; the overview keeps the count, for its size), `rule_file_mentions` (one entry per rule file, `{target, from: [...]}`, the line not quoted: it is in the text of the note it comes from), `broken_pointers` (a wikilink, backticked or absolute vault path to nothing, on any line, so a stale path after a rename shows; placeholders such as `<Name>` or `YYYY`, memory's own files and Syncthing's versions of a note, `<name>~YYYYMMDD-HHMMSS.md`, outside the vault, aren't vault notes), `skipped_imports` (`{from, import, target, why}`: an import Claude Code doesn't load, its file not on the path), `import_warnings` (`{from, import, target, warning}`: an import the snapshot warns about, its file still on the path), `not_followed`, and `cut` when a list was cut short to fit. Every check made is given, an empty list when it found nothing, so a reader tells "none found" from "not checked" (a structure leaves out only what isn't part of it: the overview's facts across every area hold two lists); a result listing `into_areas` says in a note what they are, which a cold reader took for faults (test bench, 2026-11-19), and only a result carrying the structure does (test bench's rerun: later pages repeated it). `unplaced_pointers` lists every arrival whose line doesn't say when, not only the one placing the piece. The result's `start` names a typical agent `typical`, as the call does; a `work.area` naming no area is said in a note, not only as a broken pointer (`from: work.area`); a start folder no area lists is a broken pointer `from: start.folder`, with no such note. A rule section listed on its own after its note was read whole says so in its `arrives`.
- `agent_path` without `start`: the overview, as the prototype's `typical` prints it: each typical agent's path one line per piece (`<n>. <id>  <chars> chars  #<hash>`, `[status]` with `known`, `moment: <moments>` for a piece waiting on one, ` | ` between them, without their lines, which come with that agent's own path (five paths side by side: quoting the lines of those that don't stand alone cut the overview short on the owner's vault; the field's name: the test bench's cold reader looked for a `when` field)), the tool texts as one line with a combined hash, where they come, its structure; then `rule_files_no_path_reaches` (over the typical agents, a claude.ai chat on each area and a Claude Code worker in each related folder the snapshot holds; hook scripts the PC registers count as reached) and `across_every_area`. An addition to the owner's interface, which gave `start` as required (AI suggestion). A result reporting a place no path reaches (this list, or a backward question's `matched_by` "nothing") carries a note (`_NO_PATH_NOTE`) telling it from `not_followed`: a cold reader confused the two (2026-11-19), and the explanation belongs in the result rather than the description (owner, ledger P269).
- `start.typical`, `start.role` and `start.machine` are additions to the interface's `{surface, folder, started_by}`, so an agent can name a typical agent, pick its role note and choose a PC (AI suggestion; the owner kept `typical` and `machine`, 2026-11-18: a second PC, a Linux dual boot with other repos, may come). `role: relay` adds the relay's notes. Any other role only narrows a line naming several role notes (the session-start hook's); when nothing on the path offers that choice (a "Coordinator on claude.ai", not a real case), the result says `role: … changed nothing`, so the path isn't taken for an answer about that agent (owner's choice over a refusal, which would hard-code which starts are real).
- `agent_path_reached_by`: draws every run above, keeps those reaching the place (a whole note no path reads whose rule sections paths reach is matched by them, `matched_by` saying so, test bench's rerun; a place no path holds, one that doesn't exist yet or a part of a note, is matched by its note, saying whether it holds that section, then by its area; when nothing reaches it, `matched_by` says whether it exists; a bare `hook:<event>/<script>` is matched through each of its messages; test bench, 2026-11-19), groups them by surface and chain, naming "a claude.ai chat, any area" or "a Claude Code worker, any related folder" when every one reaches it the same way, the place keeping its own id in the chain while the pieces leading to it stand for any area's (a group reached through one area only shows that area's chain, no placeholder), each group with every piece pointing to the place (`pointed_to_by`), and the structural facts across those runs. **It returns the path up to the place, not the whole paths** (owner, 2026-11-19, round 3: six places gave the same 215 pieces, about 470,000 characters): `pieces` carries, with their moments and texts, in arrival order, what those agents have in front of them when the place applies: each group's chain, the place included, every piece pointing to the place, and the start pieces (loaded at the start, session-start hook, read at the start) every agent of the group meets, the same id and hash on each of its paths. For a group reached through several areas, its first agent's chain stands for the others; the rest of those areas' pieces are lines. A piece with another text on another of those paths (the area-start hook's message names the session's folder: 24 versions on the owner's PC) is given as its group meets it, and each other version is a line of its own, `(another version, on <agent>'s path)`, with a note (test bench, 2026-11-20: one id stood for different texts, the first path's). Every other piece on those paths is one line in `other_pieces` (`<id>  <chars> chars  #<hash>`, its moments when it waits on one, each server's tool texts as one line, as the overview writes them), and `read_from` takes any of them, as a note says (`_OTHER_PIECES_NOTE`: the result models' comments aren't served; the note on withheld texts names `read_from` for these lines too, Agent paths, 2026-11-20). `known` and the budget work as in `agent_path`; a call with `known` leaves `other_pieces` out with the structure. When the texts would fit one page but for the structure's lists, those are cut first, longest first, said in `cut` and a note (`_trim_structure`); when they can't fit anyway, nothing is cut and they come over several calls. Measured on the owner's vault (engine only, without the tool texts): a section of Common-rules brings 10 pieces, about 46,000 characters, against 510,000 on those paths; Obsidian MCP's `## For agents` 18 pieces, about 130,000; Mail's 17, about 116,000; coding-practices 12, about 71,000.

## The kept drawing

Drawing every path took about a minute on the owner's server (an Atom C2750; `agent_path_reached_by` at a p50 of 50 s, 2026-11-19), each call redrawing all of them and reading every note again. Every path is now drawn once and kept (`agent_path_tools._Kept`), and both tools and the write check answer from it (owner's go on speed gains that change nothing for callers, 2026-11-19; design approved by the Agent paths session the same day).

- **What it keeps**, per vault root and `machine` argument (`_KEPT`): the setup (the vault's file list, the texts read, the rule-file definition, the areas, the snapshot, the served texts); every run of `run_starts`, each with its `Trace`; the runs calls asked for beyond those (a `work`, a start of their own), kept the same way, at most `_EXTRA_RUNS`; every file read, with its signature and digest, those the setup read kept apart; and, for the overview's list of every rule file, the rule sections each note holds, by its signature (`_SECTIONS`), so only a changed note is read again (the overview read all 6,472 notes at each call).
- **Where it lives**: in the helper process below (`_Drawer`'s), so a call no longer holds the server's one worker or its interpreter lock. The server works out the served texts (they need FastMCP and the database), hands the call to the helper (`_call_in_helper`), and shapes a refusal; the result is built there with the same functions as before, given the kept runs (`agent_paths.reached_by` takes them as `runs`). One thing at a time in the helper: a call waits for an update under way. The helper ends with the server: the plugin's `startup` task (`helper_lifespan`), cancelled by the lifespan at shutdown, asks it to stop and terminates it if a drawing still runs after 3 s (`stop_helper`), so it never outlives the server's worker (a precaution: the one SIGKILL seen on the server, 2026-11-19, isn't known to be a drawing).
- **Brought up to date before each use** (`_Kept.refresh`), from signatures: a file's or folder's mtime, size, ctime and inode. Syncthing writes a temp file, renames it into place and sets the source device's mtime, so a file can come back with an older mtime and the same size; its ctime and inode change (Agent paths' review). The file list: each folder's signature, and only the folders whose signature changed are listed again (`_Files`), since a file added, removed or renamed changes its folder's mtime; checked on a gocryptfs mount in the test container (2026-11-19: a temp-then-rename changed the folder's mtime, the file's mtime and size came back the same, its ctime and inode changed), not on the server itself. Then each file read whose signature changed is read again and compared by digest, and its new signature kept whatever the comparison found: a note read only for one section, edited elsewhere, stays watched, so a later edit of that section is seen (adversarial review, 2026-11-19: dropping it left the server notes unwatched, and the write check answered "reached" for a pointer since removed). A file that couldn't be read (missing, past `MAX_NOTE_BYTES`) is tried again at each update. Stats run on `_STAT_THREADS` threads for a large batch: on a gocryptfs copy of the vault in the container, 9,162 file stats took 0.8 s on one thread and 0.5 s on eight.
- **What is drawn again**: everything (a new `_Kept`) when the served texts changed (they carry the ledger's live area and topic names, so they can change without a deploy), or a file the setup read (the starting points, the list of areas, the rule-file definition, a snapshot beyond its `made`), or a file it looked up (an area's main note), or a snapshot came or went. A snapshot whose `made` alone changed only updates the date the results show. Otherwise only the runs a change touches: a changed note the run read whole, or a section it read of a note it read for that section only (the `<folder>/<folder>.md` pattern reads every folder note for its `## For agents` section; `Trace.sections`, so an area main-note edit outside that section redraws only the few runs reading the note whole), or a file added or removed that the run looked for (`Trace.new_file_counts`, as the write check uses it). `section` and `unfenced` are memoized on their text, which also cuts a whole drawing.
- **The reach map is this drawing's** (`_Kept.reach_map`): each update replaces the server's map whole (a path call's update sends it back too), so there is one drawing, not two caches. Its inputs are the files the setup and the runs read, as before, not those a call read for its notes (the hook scripts).
- **Checked against the old code** (2026-11-19), on a copy of the real vault in the test container, the old code (2ab0cac) and the new given the same served texts: the overview, the five typical agents and three backward questions (Common-rules, Obsidian MCP's `## For agents`, OMIQUE's machine note) gave the same JSON, first and second calls alike. Then, on that copy, after each of thirteen changes made one after the other, the kept drawing carried from one to the next (an area main note, a new note a pattern matches, a note on every path removed, a snapshot's `made`, then its content, the list of areas, a hook script, a rule note rewritten by temp-then-rename with its old mtime and size, a `## For agents` added to a note no path reads, then to a rule note, a server note edited outside its `## For agents` section, then that section, a folder renamed), the kept drawing's answers equalled a fresh drawing's. `tests/test_kelno_vault_agent_paths.py` keeps a small version of that check.
- **Costs**: the first call after a start draws everything (about a minute on the server, as before; no plugin hook starts it earlier). The drawing stays in the helper's memory: about 235 MiB peak for the whole helper on the owner's vault in the container, logged with each update. A whole drawing is still needed after the changes listed above.

## Reached, after a rule write

A note write that creates a rule note, or adds or changes rule lines, asks whether some path still reaches each rule note or section it touched (`reached_by_no_path:`, see [vault tools](vault-tools.md)); the owner asked for this warning, never a refusal, and that a check that can't run says so rather than going quiet (2026-11-19, the vault task `paths-unreached-warning`). "Reached" has one definition, `agent_paths.reached_places`: a place is on the path of one of the runs above (`run_starts`, drawn by `iter_runs`), or is a hook script the PC registers; `unreached_rule_files`, the overview's list, is every rule file it leaves out.

- **A write never draws a path.** Drawing every path took about a minute on the owner's server (an Atom C2750, measured through `agent_path_reached_by` on 2026-11-19; 1.5 s on the PC), and a first version that drew at write time, stopping at the first path reaching the place, still added 7 to 8 s to every rule write there, so it was reverted the same day. A write answers from a **reach map** (`agent_path_tools.ReachMap`), taken from the kept drawing above: for each run, every note or section on it with the vault files its chain from the start passes through, and a `Trace` of what it read and looked up (texts, sections, vault paths, note names, path patterns); and every file the drawing read, with its signature and digest (a snapshot's digest leaves out `made`, rewritten at each session's start on the PC). Those the setup reads (the starting points, the list of areas, the rule-file definition, the snapshots) are kept apart.
- **Where it is drawn** (`_Drawer`, one per vault root): the kept drawing, brought up to date in one helper process (`concurrent.futures.ProcessPoolExecutor`, spawned, started at its first use and kept, at niceness 10), so the drawing never holds the server's one worker or its interpreter lock (`--workers 1`). It runs the server's own code, reading the vault as a single-user server at that root. One update at a time; a request during one or the wait before it makes one more, `REDRAW_AFTER_SECONDS` (20 s) after the last request, so a burst of writes is one update. The first is drawn at once, started by the first note write (or path call) after the server starts.
- **How a write is answered** (`_answer`, a stat of each file the map read: about 320 on the owner's vault): a place is reached when the map has it on some path by a chain none of whose notes changed since (the written note itself aside: a note's own text never cuts the way to it), or it is a registered hook script. A place the map doesn't reach is still not reached when no path read the written note (for a note the map didn't have, new or not: when no path, nor the setup's list of areas, looked for its path, its name or a pattern matching it) and no file the map read has changed since: a changed note on a path may now point to the place, or to a note that does (second adversarial review: a test on the note naming the place missed that second hop). Otherwise, and when a setup file changed, the write says it can't tell (`ReachUnknown`), and the map is drawn again; so is it after any write, rule or not, to a note the map read. Paths are compared in lower case.
- **Cost** (owner's vault, 2026-11-19): a write's stats took 0.7 s in the test container, whose file bridge from Windows takes about 2 ms a stat; on the server's own disk, a stat takes tens of microseconds. A full draw in the container took 18.5 s, files read cold. A pattern pointer scanned every vault path for each run, most of a run's time; the matches are now kept per call (`Vault.matching`), which took every run together from 4.0 s to 1.5 s on the PC, the path tools' own calls too. With the kept drawing, an update after an area main-note edit redrew 3 of 60 paths in 0.2 s on a copy of the vault in the container, where a whole drawing took 1.5 s.
- **When it can't tell**, the result says so in one line, with why: no map yet since the server started, the last drawing failed (no snapshot, an unreadable setup input, an error), or changes since the map was drawn that may reach the place. The line points to `agent_path_reached_by`, which answers from the kept drawing, brought up to date.
- **Watching it on the server**: each update logs one line, `agent paths: reach map drawn in … s (redrew … of … paths), drawing process peak memory … MiB` (INFO); a failed one logs a warning with its error. A whole drawing says why after the count (`redrew 60 of 60 paths: <cause>`): the first drawing since the server started, which setup files changed (a snapshot's content said so), or which served texts changed (the tools by name) (Agent paths, 2026-11-20: the owner's measuring run showed whole drawings two minutes apart, from a cause the journal didn't name).
- **What the map can miss** (accepted, second adversarial review, 2026-11-19): a write doesn't walk the vault, so a file created outside the connector (Obsidian, Syncthing) is not seen until the next update: a note pointing to the place, a second note with a name a bare-name link resolved by (the link turns ambiguous; the connector writes links with full paths, which makes this rare), a new PC's snapshot. With several snapshots, `made` chooses the one the paths are drawn from, so it counts as a change then (`keep_made`). The path tools themselves miss none of these: each call brings the drawing up to date first.
- **Accepted costs of the helper**: it keeps the server's imports and the kept drawing in memory for good (its peak is logged with each update); a draw has no time limit, so one that hung would leave every unreached answer "not checked" and every path call waiting; a stop of the server waits for a draw under way (Python joins its helper at exit), which the container's stop may cut short; the draws run in the context of the request that started the first one, which only matters with several users on one root.
- **A section is a place only as the engine reads it** (`agent_paths.section`: exactly `## <heading>`, backtick fences). `rule_files.section_ranges`, which the write checks and `open_area` use, also takes `## For Agents`, a closing `#`, a tab or a tilde fence; such a section is served by `open_area` but is no piece of any path, and is in neither the overview's list nor this check (adversarial review, 2026-11-19: the write check named it, and asked for a pointer that could not help). The engine's reader differing from `open_area`'s is older than this check and open.

## Not followed

Said on each path it concerns: what a hook script that can't say its messages would print (`messages: null` in `hook_messages`, by name), and all hook messages at other events when the snapshot predates that key; what the Claude desktop app adds at a session's start; claude.ai's own system prompt and memory instructions; `open_area`'s data lines (map, entries, tasks: data, not rules). Said on every path (in the overview, once, under `across_every_area`): what the tools leave out by design, in the vault's words (see "In a repo, the tools stop at what Claude Code loads" above). The work's `kind` is recorded but not yet matched against the pointers' moments.

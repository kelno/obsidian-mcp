# Agent paths: `agent_path` and `agent_path_reached_by`

> Read before touching `src/plugins/kelno_vault/agent_paths.py` (the engine), `agent_path_tools.py` (the two tools) or `agent_path_result.py` (their results). Fork-only (see `FORK.md`), tools of the `kelno_vault` plugin, served only with it loaded ([plugins](plugins.md)).

The fork owner's vault holds the rules its agents follow, spread over notes, `## For agents` sections, hooks on the owner's PCs, Claude's memory and this server's own tool texts. Which of them a given agent actually meets, and in what order, was written by hand and drifted. These two tools draw it from the setup as it is, so an agent changing a rule can see who meets it and what is around it (owner's design, 2026-11-18; the vault note `Areas/Agent personnel/Agent paths/Agent paths - path tool.md` holds the design and the owner's decisions):

- `agent_path(start, work, known)`, forward: "I'm this agent, doing this work: what do I meet?"
- `agent_path_reached_by(place, known, machine)`, backward: "this rule lives here, or would: who meets it, and what's around it?"

Both read-only, admission class `scan` (each call reads the vault's rule notes; adding them moved `TOOL_CLASSES`, so `CLASS_MAPPING_VERSION` is 9).

## Where it comes from

The tools were first built as a script on the owner's PC (`agent_paths.py` in a plain folder, its prototype). The owner moved them here (2026-11-18): a claude.ai chat cannot run a script on the PC, and only this server has its tool texts as served. The engine is that script's reading rules, ported line for line, with its input swapped; its pieces, ids and hashes are the prototype's, so the two can be compared. On 2026-11-18, run on the real vault with the fixture's tool texts, it gave the same pieces (ids, hashes, stages, moments, order), the same structural facts and the same unreached rule files as the prototype's `typical` for all five typical agents. Change a reading rule here, not there: the prototype is no longer maintained.

## What it reads

The tool wrapper (`agent_path_tools.py`) gathers four inputs; the engine (`agent_paths.py`) imports nothing from the server, so it also loads on its own.

1. **The vault**, through the caller's root: every visible file (hidden folders and files left out, as the file tools do), each read with `read_bytes` (`MAX_NOTE_BYTES`) and decoded as Python's universal newlines read it on a PC (`CRLF` and lone `CR` become `LF`), so hashes match the PC's. From it: the rule-file definition (`rule_files`, `_/Rule files.md`; unreadable is a refusal, since without it no pointer can be told from a mention), the list of areas (`areas_index`, `Areas/Areas.md`; unreadable is a note), Claude's memory through its mirror note (`MEMORY_NOTE`). (The engine can still read the hand-written paths, `WHERE_NOTE`'s `HANDWRITTEN_HEADING`, as the prototype did; the tools no longer show them: ledger P251 replaces that list with these tools.)
2. **The starting points**, `STARTING_POINTS_PATH` (`_/agent-paths/starting-points.toml`), the only hand-written input: what each surface loads first (a fact of the product no file states: claude.ai starts from memory; Claude Code loads `~/.claude/CLAUDE.md`, the folder's `CLAUDE.md` files, then its session-start hooks) and the five typical agents, each a surface, a folder, who started it and a role, numbered as in the hand-written list. It lives in the vault, not here, because it names folders on the owner's PC, and this repo is public (AI suggestion). Since ledger P251 it is the reference for the loading order: `WHERE_NOTE`'s "Loaded at the start" points to it, and a new kind of agent is added there. Unreadable is a refusal.
3. **The PC side**, `SNAPSHOT_FOLDER/<machine>.json` (`_/agent-paths/`): what only a PC sees, written by a session-start hook on each PC (the vault's `_/claude-code-hooks/agent-paths-snapshot.py`) in the background, rewritten only when its content changed, carried here by the vault's sync. Formats 1 and 2 (`SNAPSHOT_FORMATS`; another format is left out with a note): `machine`, `made` (when the PC side last changed), `vault` and `home` (where they are on that PC), `folders` (for the vault, the home folder and each related folder of the list of areas that exists on that PC: `loads`, the files Claude Code loads at the start in order, each `note:<vault path>` or `file:<PC path>` with how it arrives, imports included; `session_start`, each session-start hook's message on a sample start there, with its hash), `files` (the text of each `file:`), `hooks` (every hook registered, by event and matcher), `relay_notes` and `relay_config`; format 2 adds `hook_scripts`, each registered hook script's id (`note:<vault path>` or `file:<path>`) and the digest of its file as the snapshot ran it. A hook script is a vault file, read live here: when one on the path differs from that digest, the result says its message may be out of date, and how to refresh it (`agent-paths-snapshot.py run` from a Claude Code session on that PC; from claude.ai, ask the owner or a desk session). Owner, 2026-11-18: the tool says when the snapshot is out of date and what to do, instead of a rule teaching it. On the PC the hook also refreshes the snapshot after an edit to its inputs and after a git command that can change a checkout, so this mostly covers edits made from claude.ai; the repo files the server can't see (`file:` pieces) have no such check. Several PCs: `start.machine` / `machine` picks one; without it the most recent `made`, with a note. A start folder the snapshot does not hold uses the deepest folder above it that it does, said under `not_followed`. No snapshot: the Claude Code side is said to be missing, never guessed.
4. **This server's texts as served**: `tools/list` unscoped (`FastMCP.list_tools`, the full list whatever the caller's credential, since a path is about a kind of agent), each tool's description followed by each top-level parameter's description, every loaded plugin's lines included; the server instructions; the server's part of `get_vault_guide` (`tools.vault_guide_server_part`, the one function both use, so the guide is hashed exactly as served); `open_area`'s instruction lines (`OPEN_AREA_INSTRUCTIONS`).

## Pieces

Each piece has an id naming what it is: `note:<vault path>`, `section:<note path>#<heading>`, `file:<PC path>` (a file outside the vault Claude Code loads), `hook:<event>/<script>`, `memory:/preferences.md` and `memory:/profile.md`, `tool:obsidian-mcp:<tool>`, and three this server adds beyond the prototype: `instructions:obsidian-mcp`, `guide:obsidian-mcp` and `tool:obsidian-mcp:open_area/instructions` (AI suggestion). Its hash is the first 12 hex digits of its text's sha256, the PC hook's own digest; the hash only assures nothing changed (owner).

A piece's `stage` orders the path, by when it reaches the agent: loaded at the start, session-start hook, read at the start, at the first bridge result, when the work's area is opened, when its moment comes, when the connector's tools load. Within a stage, pieces that arrive whatever the conversation brings come before those waiting on a moment, and a pointer that says when before one that doesn't; then the order they were met. The first arrival of an id wins; later pointers to it are listed in `also_pointed_by`.

## Reading rules (from the prototype)

- **What loads by itself**: on Claude Code, the snapshot's top-level loads for the folder, in the steps `starting-points.toml` names: the user `CLAUDE.md` (`user_claude_md`; an entry the snapshot marks `exists: false` loads nothing), the files of `~/.claude/rules/` (`user_rules`), the folder's `CLAUDE.md` files and its own rules folder (`folder_claude_md`), then the `@` imports of each loaded `.md`, followed recursively (resolved as Claude Code does: `~` is the PC's home, a relative path is against the importing file). Only what Claude Code loads expands imports. An import the snapshot lists in the folder's `skipped_imports` (in a project's file, one outside the session's folder, which Claude Code holds for an approval the desktop app never asks for; the user `CLAUDE.md` is exempt) is not loaded: it shows in `structure.skipped_imports`. An imported file whose snapshot entry carries a `warning` (its import line sits next to another import, which made both fail to load in some tests, Q134) stays on the path, as the snapshot lists it loaded: its `arrives` ends with "(may not load: …)", and the warning shows in `structure.import_warnings`. Taking it off the path would claim more than the tests show (`@./rel.md` loads next to other imports).
- **Hooks**: the session-start messages of the folder's snapshot entry; a hook that prints nothing puts nothing on the path. A line naming several role notes (`_/agent/roles/`) keeps only the start's role note.
- **Pointers in rule files**: wikilinks, backticked vault paths ending `.md` and absolute paths ending `.md`, each with the sentence holding it. A pointer's moment is the guide index's "when to read it" (`- [[guide]]: when`), or the line's or sentence's leading condition (`When…`, `Before…`, `At the start…`, `Voice only…`, …), `when met` for a reading verb aimed at it, else `unplaced`. "At the start" and "While…" hold from the moment the pointer is met; any other condition makes the piece wait on its moment. A link to a rule file is followed when it says when (a moment) or "read"; one that says neither is a mention, not a pointer (owner's rule, ledger P250: a pointer to another rule note starts with when to read it, or follows the guide index's shape), listed in `rule_file_mentions` and not put on the path. A link to another note with no reading verb is a mention too, counted, not followed; read, such a note is followed for its rule sections only. A file outside the vault (a repo's `CLAUDE.md`) is not followed beyond its imports.
- **The work's area**: what `open_area` serves, rebuilt from the files: the main note's `## For agents` section, the main note without that section and its Tasks section (its links followed to rule files only, and reported when they are), Vault conventions' "Working on an area", coding-practices when the main note sets `code_project: true`, and `open_area`'s instruction lines as served. A Claude Code session in a folder an area lists gets that area without `work`.
- **Tool texts**: the server's texts as served, at the last stage.

## Results

- `pieces`: each with `id`, `stage`, `arrives` (in words), `always`, `where`, `chars`, `hash`, `via` (the pointing line, cut at 240 characters with "…": the whole line is in the text of the piece that points), `moment`, `also_pointed_by`; with `known`, `status` (`new`, `changed`, `unchanged`), and `text` only for new or changed pieces. Without `known` every text comes. On a first call (no `known`) every piece is listed, one whose text comes in a later call (`text_withheld`) in **short form** (`id`, `stage`, `always`, `moment`, `hash`), its details coming with its text. A call with `known` lists only what it brings: the pieces with their text this time, those now marked in parts, new private ones; the pieces held and those still waiting were in the first call, so they are left out, counted in `waiting`, and a removal shows in `left_path` (owner, 2026-11-18: repeating them took most of each call on a backward question, one or two texts per call). A piece that joins the path between calls arrives whole when its turn comes. The `structure` and a backward question's `reached_by` are left out of such a call too (owner, 2026-11-18: 9,000 characters a call on a backward question); a call without `known` shows them again.
- **The size budget**: a first call's texts run past 100,000 characters on most paths (the tool texts alone are over 100,000), and the details of a backward question's 150 pieces alone reached 50,000 on the owner's vault. Every result is held to `PAGE_CHARS` (80,000), 1,000 kept for notes: twice the server's read cap (`MAX_READ_RESPONSE_CHARS`, 40,000, which every other tool keeps), on trial since 2026-11-18 (owner), since at 40,000 reading a whole path took 12 to 20 calls. Claude Code refuses to show a model a connector result past `MAX_MCP_OUTPUT_TOKENS` (25,000 tokens by default; this JSON, hashes and paths, runs about 2.3 characters a token, so a 59,000-character result was refused and saved to a file): the owner's PCs set it to 50,000 in Claude Code's settings (New PC setup). Claude Code also saves to a file, whatever its tokens, any result past 50,000 characters unless the tool's `tools/list` entry declares `_meta["anthropic/maxResultSizeChars"]` (live check 3 found 75,000 to 79,000-character results saved to a file with the token limit raised): both tools declare 100,000, through the plugin tool's `meta`. A PC without the setting gets a page past about 59,000 characters as a file to read. The first live call (2026-11-18) found it wasn't: the overview was 222,000 characters (each agent's `rule_file_mentions` quoted 60-odd whole lines) and a backward question 59,000, every text wrongly marked in parts; hence the shape below. Texts are filled in path order while they fit (by an estimate, then the whole result measured and the last texts taken back until it fits); the rest are marked `text_withheld`, in short form, with a note to call again passing as `known` the hashes of the pieces whose text the caller now holds; those withheld are then new, and come next: `known` is the mechanism the design already gives (AI suggestion). Every call makes progress, so a caller doing that gets every text in a bounded number of calls: the first text due either arrives or is marked `text_in_parts`. A text larger than the room it would have (on a large path, a 30,000-character note; the obsidian-mcp repo's own `CLAUDE.md` was 82,000 characters until its cut on 2026-11-18) is marked `text_in_parts` (promising it "next" could send the caller round forever) and comes in parts (owner, 2026-11-18, so a claude.ai chat, which can't read a PC file, gets it too): a call with the same arguments plus `read_from: {id, offset}` returns that piece alone, its text from `offset` as far as the budget allows (often whole in one part), with `text_offset` and `next_offset` (none after the last part); the hash is the whole text's. Past the budget even in short form (some 400 pieces), the last pieces waiting for their text are left out and the structure's lists cut short (`cut`), said in the notes. The overview is bounded the same way: structure lists cut from the last typical agent back, then piece lines, a cut path ending on how many it leaves out.
- **The tool texts are short on purpose** (owner, 2026-11-18): the descriptions and parameter texts say only what an agent needs to call the tool, and the result models carry comments, not docstrings, since a model's docstring is sent with the tool's schema. How to read a result (what a piece is, its stage, `known`, the structural facts) lives in the vault note the descriptions end on, `_/agent/Where agent instructions go.md`, where agents changing a rule already look.
- `left_path`: with `known`, the held pieces no longer on the path, so a caller comparing against its hashes sees a removal, which no status can show (found by the cold reader, 2026-11-18).
- **Private notes**: a piece in a private folder (`PRIVATE_FOLDER_NAMES`) is marked `private` and never carries its text (P98).
- `structure`: facts, never judgments (owner): `size` (characters and pieces always on, waiting on a moment, and tool texts), `unplaced_pointers`, `pointers_outside_rule_files`, `into_areas` (trunk into a leaf, or leaf into another leaf), `mentions_not_followed` (a count), `rule_file_mentions` (one entry per rule file, `{target, from: [...]}`, the line not quoted: it is in the text of the note it comes from), `broken_pointers`, `skipped_imports` (`{from, import, target, why}`: an import Claude Code doesn't load, its file not on the path), `import_warnings` (`{from, import, target, warning}`: an import the snapshot warns about, its file still on the path), `not_followed`, and `cut` when a list was cut short to fit.
- `agent_path` without `start`: the overview, as the prototype's `typical` prints it: each typical agent's path one line per piece (`<n>. <id>  <chars> chars  #<hash>`, `[status]` with `known`, `when: <moment>` for a piece waiting on one), the tool texts as one line with a combined hash, its structure; then `rule_files_no_path_reaches` (over the typical agents, a claude.ai chat on each area and a Claude Code worker in each related folder the snapshot holds; hook scripts the PC registers count as reached) and `across_every_area`. An addition to the owner's interface, which gave `start` as required (AI suggestion).
- `start.typical`, `start.role` and `start.machine` are additions to the interface's `{surface, folder, started_by}`, so an agent can name a typical agent, pick its role note and choose a PC (AI suggestion; the owner kept `typical` and `machine`, 2026-11-18: a second PC, a Linux dual boot with other repos, may come). `role: relay` adds the relay's notes. Any other role only narrows a line naming several role notes (the session-start hook's); when nothing on the path offers that choice (a "Coordinator on claude.ai", not a real case), the result says `role: … changed nothing`, so the path isn't taken for an answer about that agent (owner's choice over a refusal, which would hard-code which starts are real).
- `agent_path_reached_by`: draws every run above, keeps those reaching the place (a place that does not exist yet is matched by its note, then by its area: `matched_by`), groups them by surface and chain, naming "a claude.ai chat, any area" or "a Claude Code worker, any related folder" when every one reaches it the same way, and returns the union of their pieces (same `known` mechanism and budget) and the structural facts across those runs.

## Checking it against the prototype

The prototype stays on the owner's PC (`D:\work\agent-paths`, outside this repo). To compare after a change to the reading rules: load `agent_paths.py`, `rule_files.py` and `areas_index.py` by path (`rule_files` imports the server only inside `read`, for this), build a `Setup` from the local vault with the fixture's tool texts, and compare each typical agent's non-tool pieces (id, hash, stage, always, moment, arrives) and structure with `agent_paths.py typical --json`.

# Task tools: the Tasks plugin's format, read and written server-side

> Read before touching `list_tasks`, `create_task`, `edit_task`, `set_task_status`, `src/services/fork_tasks/`, `fork_note_tasks` or migration 1001. The write tools are on the destructive-write surface: [vault tools](vault-tools.md) applies to them in full.

Four tools let an agent read and change the to-dos in the vault, written in the [Obsidian Tasks plugin](https://publish.obsidian.md/tasks/)'s emoji format (`- [ ] Call the bank ⏫ 📅 2026-11-05`). Fork-only (see `FORK.md`).

## The requirements this design answers to

Set by the owner, and they outweigh any technical choice below:

1. **Use the plugin's own interface rather than imitating it.** The format is the plugin's documented emoji format, and each tool is mapped to the official command or API function it mirrors (table below).
2. **It works with the owner's PC off.** Everything is server-side: no running Obsidian is needed or contacted.
3. **Same question, same answer as the plugin in Obsidian.** `list_tasks` returns the tasks a Tasks query block asking the same question returns; the write tools write the lines the plugin itself would write.
4. **Writes never guess.** Every write is checked against the line and the note's hash it was based on, and refused if either changed. A write naming the task by its id finds it in the note as read in that call, and is refused when no task or several carry the id; the note's hash stays optional there (see "Task ids").
5. **A recurring task is never ticked without its next occurrence.** A `🔁` rule the tools can follow is ticked with it, written as the plugin writes it; any other rule is refused, with nothing written.
6. **Tasks are named by an id, not by a note and line number** (owner, 2026-11-16). A line number goes stale as soon as a line above it moves, silently, wherever it was written down. In this vault every task carries a `🆔`; line addressing remains only for a task with no id. See "Task ids".

## Ported from the plugin's source, not its documentation

The plugin's documentation does not say enough to reproduce it exactly (field order on write, what happens to trailing tags, which status types count as done, the default sort). So `fork_tasks/format.py` is a function-by-function port of the plugin's TypeScript at **version 8.6.0**, the version installed in the reference vault, with each function naming what it mirrors (`DefaultTaskSerializer.deserialize`, `Task.handleNewStatus`, `Urgency.calculate`, `Sort.defaultSorters`, …). JavaScript semantics that differ from Python's are reproduced on purpose: ECMAScript whitespace for `\s` and `trim()`, `.` not matching U+2028/U+2029, ASCII-only `\d`, first-match `replace`.

**When the plugin is upgraded**, re-read these files in its source and compare: `src/Task/TaskRegularExpressions.ts`, `src/TaskSerializer/DefaultTaskSerializer.ts`, `src/Layout/TaskLayoutOptions.ts` (field order), `src/Task/Task.ts` (`fromLine`, `handleNewStatus`, `createNextOccurrence`), `src/Task/OnCompletion.ts`, `src/Task/Recurrence.ts` and `src/Task/Occurrence.ts`, `src/Task/Urgency.ts`, `src/Query/Sort/Sort.ts`, `src/Statuses/StatusRegistry.ts` (`getNextRecurrenceStatusOrCreate`), `src/Query/Filter/*` for the filters in `fork_tasks/query.py`, `src/ui/EditableTask.ts` and `src/Commands/CreateOrEditTaskParser.ts` (the dialog).

What the port says that is easy to get wrong:

- **Fields are read from the end of the line**, in a loop (at most 20 rounds), in this order per round: priority, ✅, ❌, 📅 (also 📆 🗓), ⏳ (also ⌛), 🛫, ➕, 🔁, 🏁, a trailing `#tag` (put back into the description), 🆔, ⛔. A field written before ordinary text stays in the description as text (reported as the warning `field_in_description`).
- **Every plugin write re-serializes the whole line** in its fixed order — description, 🆔, ⛔, priority, 🔁, 🏁, ➕, 🛫, ⏳, 📅, ❌, ✅, block link — whatever order the line was in, with two or more trailing spaces (a Markdown hard break) kept. So do these tools: after `edit_task` or `set_task_status`, a line whose fields were out of order comes back in canonical order. That is the plugin's own behaviour, not a side effect of ours.
- **An unregistered status symbol is type TODO** (`createUnknownStatus`), so `[X]` is not done unless `X` is set up as a status.
- **`done` means DONE, CANCELLED or NON_TASK**; `not done` the rest.
- **A done date is added only when the status type becomes DONE from another type**, kept while it stays DONE, removed when it leaves DONE; the same for ❌ and CANCELLED; each only when its setting is on.
- **`🏁 delete` removes the line** only when the type becomes DONE from another type (not on cancel).
- **A recurring task becomes two lines** when its type becomes DONE from another type (`handleNewStatus`): its next occurrence, then itself, or the reverse with "next recurrence appears on the line below" (`recurrenceOnNextLine`); `🏁 delete` then removes only the completed one. Cancelling, un-ticking or any other change writes no next occurrence.
- **The next occurrence** (`createNextOccurrence`, `Occurrence.next`) copies the task as it was before the change, with: the status that follows DONE in the cycle, or the first TODO, then IN_PROGRESS, reached from it (`getNextRecurrenceStatusOrCreate`); start, scheduled and due moved by the distance from the reference date (due, else scheduled, else start; due, start, scheduled with "remove scheduled date on recurrence", which also drops `⏳` when `🛫` or `📅` is there) to its next date, counted from today with `when done`; no `✅`, `❌`, `🆔`, `⛔` or block link; `➕` today only with "set created date", otherwise none. A task with no reference date still gets one, with no dates.
- **The plugin rewrites a rule in its own wording** on every rewrite of the line (`Recurrence.toText()`, rrule's `toText`): `every Monday` becomes `every week on Monday`. So do the tools, on every write of a recurring task's line.

## Which lines are tasks

The plugin reads only list items Obsidian's own parser marks as tasks, then applies its line pattern (indentation of spaces, tabs or `>`; a marker `-` `*` `+` `1.` `1)`; one or more spaces, not tabs; `[c]` with any one character). Obsidian's parser is not open source, so `fork_tasks/scan.py` rebuilds the part of its decision that matters:

- frontmatter is skipped, through the repo's one partition;
- fenced code is skipped, through the repo's one fence grammar (`links.scan_fences`), never a private one. Its inline-code masking is not used, since a task may hold inline code;
- an escaped `- \[ ] text` matches nothing and is not a problem: the vault's legacy checkboxes were converted to that form on purpose;
- what might or might not be a task is a **problem** row with a reason, reported by `list_tasks` and never dropped: `inside_comment` (`%% … %%`), `inside_html_block` (CommonMark types 1–6), `inside_math_block` (`$$ … $$`), `inside_frontmatter` (a line-1 block whose fences close but whose YAML does not load: still frontmatter to Obsidian), `indented_outside_list` (4+ columns outside a list: code or paragraph text in CommonMark), `unusual_indentation` (NBSP or another non-space whitespace before the marker), `no_space_after_checkbox` (`- [ ]text`), `line_separator_in_line` (a U+2028 / U+2029 inside the line: the plugin reads only what comes before it, so a rewrite would drop the rest), and the near misses `whitespace_after_marker` (a tab or NBSP between marker and box), `no_space_before_checkbox` (`-[ ]`), `empty_checkbox` (`- []`); plus the bounds `line_too_long` and `rows_capped`.

**To check once in Obsidian** (by eye; the plugin has no query API): put each case in a note with the query `not done` and confirm what it lists. If Obsidian disagrees on one, it becomes a declared divergence here.

| Case | The tools say |
| --- | --- |
| `- [ ] a` inside `%%` … `%%` | problem `inside_comment` |
| `- [ ] a` inside `<div>` … `</div>` (no blank line) | problem `inside_html_block` |
| `    - [ ] a` after a blank line, no list above | problem `indented_outside_list` |
| `\t- [ ] a` at the top of a note | problem `indented_outside_list` |
| `- [ ]text` | problem `no_space_after_checkbox` |
| `- [ ] a` between `$$` lines | problem `inside_math_block` |
| `- [ ] a` preceded by an NBSP | problem `unusual_indentation` |
| `- [ ] a` inside a frontmatter block whose YAML does not parse | problem `inside_frontmatter` |
| `- [ ] a` in a callout `> - [ ] a` | task |
| `- [ ]` with nothing after | task |
| a task after an indented fence opener nothing closes | task, but every write to the note is refused |

## The owner's settings

Read from the vault on every call, once per call (`TASKS_PLUGIN_SETTINGS_PATH`, default `.obsidian/plugins/obsidian-tasks-plugin/data.json`), through the root's anchored descriptor with no symlink followed; never written. Used: global filter, global query, created/done/cancelled date settings, statuses (core then custom, the first per symbol), use-filename-as-scheduled-date and its format and folders. An absent file means the plugin's own defaults, said in every `list_tasks` result (`settings.source`). A file that is not JSON, has a field of the wrong type, or sets a format other than the emoji format refuses every task tool (`task_settings_invalid`). A file-name date format other than `YYYY-MM-DD` / `YYYYMMDD` is refused the same way.

**The global filter**: a line without it is not a task at all; it is removed from the tag list; `create_task` puts it in front of the description, as the dialog does; `edit_task` puts it back in front when the dialog would. In both, whole-word copies of it in the `description` argument are dropped first (T12), so it is written once. **The global query**: applied to every `list_tasks` call, line by line, through the same parser as the tool's own filters; one line the tools cannot apply refuses the call, naming it.

## `list_tasks`

Each argument is one Tasks query line (the table is in `fork_tasks/query.py`), and the result's `query` field is the whole block, so the same question can be pasted into Obsidian. `tags include` is a case-insensitive substring of any tag (`#area/x` matches `#area/x-y`); `path includes` a case-insensitive substring anywhere in the path, `.md` included; dates follow `DateField` (a missing date matches only `starts`; an invalid one never compares); `happens` is any of start, scheduled and due. Tags in a note's frontmatter do not count: the plugin's tags are the line's.

The default sort is the plugin's (status type, urgency, due, priority, path), so "the first five" agree; `limit` applies after it.

**Private folders** (fork, F63, owner's decisions 2026-11-12 and 2026-11-13, P98): with private folders configured (`PRIVATE_FOLDER_NAMES`, one definition for every tool: "Private folders" in [search](search.md)), the content of their notes stays out of what agents come across, and a query not limited to a path returns tasks from the whole vault. So a task in such a note is listed by location only (`ref`, `path`, `line`, `status_type`, `private: true`), a problem without `text`, a stale task without `indexed_text`, and a `notes` line says why, as `open_area` and the ledger's citing tasks do. `include_private=true` lists them in full; naming a private folder in `path` no longer does (it did until P98: one mechanism, the argument, everywhere). Without the setting nothing is private and the argument does not exist. Filters still apply to the hidden text, so a `text` match shows that a private task contains the word: accepted, as for the searches' count. The write tools act on a note the agent names, so their results keep the line.

**Blocked tasks are not shown yet** (owner's decision, 2026-11-15: not built while chained tasks aren't in use, and not on any to-do list). `list_tasks` returns a task's `⛔` ids as text but not whether the tasks they name are still open, so an agent asking "what's next?" may pick a task that is waiting. If it is ever needed: mark a task that waits for an open one, naming which, and accept the plugin's own query lines `is blocked` / `is not blocked` (`Task.isBlocked`: a finished task is never blocked; the ids are resolved across the whole vault, as `check_task_ids` already does for writes).

**Freshness**: the index finds the candidates; then each returned task's note is read from disk (at most `limit` notes), the line compared, and the note's real `content_hash` returned. A line that changed since the index read it goes to `stale`, never returned as current. The hash is the wire digest of the raw bytes (vault-tools L6: not `notes_metadata.content_hash`).

## The write tools

Each one runs the repo's write ladder unchanged — `_require_write`, `_precondition_syntax_error`, `open_mutable`, `_leaf_state_error`, the bounded read, `_precondition_error`, `_note_size_error`, `_confirmed_publication(write_file_at(…, expected=…))` — so the anchored-write guarantees, the two windows (`stale_precondition`, `concurrent_write`) and the vault-assignment confirmation all hold as for `edit_note`. On top:

- `edit_task` and `set_task_status` name the task by `id` ("Task ids", below), or by `path` + `line` + `expected_line` + `expected_hash`, all four (`invalid_argument` naming the missing ones); the line at `line` must equal `expected_line` (`line_mismatch`) and must be a task the plugin reads (`not_a_task`).
- **Only that line changes, one line is added, (`🏁 delete`) that line is removed, or (a recurring task ticked done) that line becomes two.** Every other byte is copied, terminators included (CRLF stays CRLF). Removing the last line of a note with no final terminator also removes the terminator before it, as the plugin's `lines.splice(…).join('\n')` does; two lines written in place of a last line with no terminator keep the note without one, the first taking the note's usual terminator.
- **The written lines are read back** before anything is published: the new text is scanned again, each line must be a task there and parse to exactly the intended task. This catches a description ending in something the plugin reads as a field, and a task appended inside an unclosed code fence.
- **Every other line must read exactly as before.** The note is scanned before and after the write, and every other task or problem line must keep its kind, reason and text at its (shifted) number. A written line holding an unpaired `%%` is refused outright, since it would open an Obsidian comment hiding the rest of the note even where no task follows.
- **A line the plugin would damage is refused**, not rewritten: an invalid date (the plugin writes `Invalid date`), an unknown `🏁` value (its parser drops it), the same field given twice (`duplicate_field`: the plugin keeps one and drops the other).
- **A note with an indented fence opener nothing closes is refused**, as `edit_note(section=…)` refuses it: whether the lines below are code cannot be decided.
- **Recurring tasks**: the dates come from upstream's `src/services/task_recurrence.py` (#428), used as it is: a closed list of rule shapes whose dates the plugin's documentation and tests pin (every day / N days / weekday / week / N weeks / week on weekdays / month / N months / month on the Kth / month on the last / year / N years / a month on the Kth, each optionally `when done`), refusing every other rule rather than guessing, and a yearly rule from February 29. The fork adds the plugin's side in `fork_tasks/recurrence.py`: the wording (`canonical_text`) and the next occurrence (above). A task whose rule is outside that list is refused by `set_task_status` and `edit_task` (`recurring_task`), telling the agent to tick or edit it in Obsidian; `edit_task` can still replace or clear that rule (`recurrence`, `clear`). `create_task` and `edit_task` take a rule from the list, written in the plugin's wording, and refuse a recurring task with no due, scheduled or start date, as the plugin's dialog does; a write that sets the rule or a date also computes the next occurrence once and refuses dates the rule cannot be followed from (yearly from February 29), naming them, so the problem shows when the task is written. At the tick, a refusal says whether the rule or the task's dates are the cause (`recurring_task` either way), and offers replacing the rule only for a rule. A tick whose next occurrence lands on a date already past (the plugin counts from the old date, missed occurrences included) says so in the result, and un-ticking a done recurring task says its next occurrence, if one was written, is still in the note. `set_task_status`'s result keeps `line`, `ref` and `text` for the ticked task, where it now is (no text when `🏁 delete` removed it), gives the new occurrence in `next_occurrence` and `next_occurrence_line`, and says the lines below moved. An interval of 101, 201 … 901 is refused: rrule writes it in the singular (`every 101 day`, its `plural` is `n % 100 !== 1`), a wording upstream's parser does not read back.

**Task lines are written by the task tools only** (fork, owner's decision, 2026-11-12; the `kelno_vault` plugin's `check`, `src/plugins/kelno_vault/task_lines.py`, since 2026-11-13: without that plugin the note writers don't check task lines). `edit_note` (every mode, `dry_run` included), `create_note` and `write_file` on a `.md` refuse, with `task_line_by_hand` and nothing written, a write whose new text holds a task line the old text did not hold as it is. A task line is what the index pass would store as one: a line `task_scan.scan_note` finds (outside fences and frontmatter) that `task_ops.parse_line`, under the owner's Tasks settings and global filter, reads as a task. Old and new are compared as a multiset of such lines, without surrounding whitespace, so deleting a task line or moving one unchanged within the note passes; a changed line is a removal plus an addition, and is refused. Bytes that are not UTF-8 are read leniently, so they cannot switch the check off. The check runs before the agent-edit stamp, the size cap and the dry-run diff, after the core's note-name refusal; like every plugin check, one that raises is set aside with a `plugin_error:` line and the write goes ahead ([plugins](plugins.md)); it skips the scan when the global filter does not occur in the new text, and lets the write through (logged at debug) when the Tasks settings cannot be read or applied (a file-name date format the task tools don't implement), or when the vault has no Tasks settings file (the plugin's defaults have no global filter, which would make every checkbox a task in a vault that may not use the plugin). Not checked, so that the existing answer wins: `create_note` or `write_file(overwrite=False)` on an existing note (`already_exists`), and a `write_file` overwrite whose old text could not be read (every task in it would look new). Not covered: `move_note`'s link rewrites (the server's own change, inside task lines too), `import_from_url`, and uploads (`request_upload` to a `.md`). Limitations found by the adversarial review (2026-11-12), accepted: lines the scanner reports as problems rather than tasks (`- [ ]#task`, a BOM or NBSP lead, a task inside an HTML block) pass, as they do in `list_tasks`; tasks past the scanner's 10,000 rows or longer than 10,000 characters are not compared; closing a fence that hid task lines makes them new tasks and is refused (delete and recreate them with `create_task`); and no tool moves a task to another note (recreate it there, then delete the old line). The refusal names up to ten lines and the task tool to use. Accepted with the move into the plugin (adversarial review, 2026-11-13): a bug inside the check now lets the write through with `plugin_error:` instead of failing it, and a plugin listed before `kelno_vault` whose check refuses wins over `task_line_by_hand`.

**Ledger citations.** After the write, the three tools read the written line (for a `🏁 delete` removal, the removed one) for agent-ledger citations (`[F12]`, `[Q14, P3]`) and return `ledger_refs`: each cited entry, any kind, as it stands now (kind, title, status, a quirk's certainty, the day it last changed) with the state of every task citing it (the written note counted from the text just published, so even when the immediate re-index could not run); a bare `F12` naming an existing entry gets a note. A write that closes a task also says, in `notes`, what that means for each cited entry (ledger F51: feedback whose tasks are now all done is to be closed as `handled`; see "Task links" in [agent ledger](agent-ledger.md)). A failure there is a note, never a failed write. The task format itself is untouched: the citation is ordinary description text. See [agent ledger](agent-ledger.md), "Task links".

`create_task` writes the dialog's line: `-` marker, no indent, status todo unless given, ➕ today if `setCreatedDate`, area tags appended to the description. Placement: after the last non-blank line of the `heading` section's own lines — above its first subheading, so a task added under `## Tasks` never lands under `### Done` — (the repo's section resolver, over the frontmatter-stripped body), or of the note. A scheduled date the plugin takes from the file name (`useFilenameAsScheduledDate`) is not on the line and is left out of the read-back comparison. `expected_hash` is optional there.

## Task ids

Every task in this vault carries the plugin's `🆔`, and the tools name tasks by it (owner, 2026-11-16, after a tracker outside the vault kept a `Mail.md:40` that went stale silently). The id is the plugin's own field, so the plugin shows it and its dependencies (`⛔`) use it; a hash of the line would change at every edit, and an Obsidian block ref (`^abc`) means nothing to the plugin.

- **Addressing.** `edit_task(id=…)` and `set_task_status(id=…)`: the index lists the notes whose task rows carry the id (`_task_paths_with_id`); each is read from disk and the task found by its id in the text as it is now (`ids.lines_with_id`), so a task whose line moved since the last pass is still found; the write then runs the ladder above, finding the task by its id again in the very bytes it reads (the ones the publish compares against), not at the line number of the first read. An index-listed note that cannot be read (too large, not UTF-8) or past the 20 read counts as possibly holding the id: with one copy found elsewhere, `task_id_ambiguous` rather than a guess. The write permission is checked before any lookup. `path` narrows the search to one note and is read even when the index does not list it (a note new since the last pass, T10). No task: `task_id_not_found`. Several, in one note or in several (a line copied in Obsidian, a sync-conflict copy): `task_id_ambiguous`, naming each; `path` chooses between notes, and a duplicate within one note is renamed by line (`new_id`). `expected_hash` is optional by id: the line is the one the call reads, and the in-call compare covers its read-to-publish window. `id` with `line` or `expected_line` is `invalid_argument`. Results carry `id` (and `next_occurrence_id`), and `list_tasks`, `open_area` and the ledger's citing tasks give each task's `id` first, a private task's included (an id is a name, not its text). A task in a private folder found by its id alone (no `path`) comes back without its text (`text`, `previous_text`, `next_occurrence`), since the agent never named the note (P98, found by the adversarial review); naming the note with `path`, or reaching it by line, keeps the text, as for every write tool. A recurring task's done occurrence reached by id (an id stored before ids moved, or a tick in Obsidian) answers `changed: false` with a note pointing to its next occurrence.
- **`edit_task(new_id=…)`** sets or renames the id (it was `id` until 2026-11-16, when `id` became the address).
- **`TASKS_ALWAYS_ID`** (default off; on in this vault's deployment): `create_task` makes up an id when none is given; a recurring task ticked done hands its id to its next occurrence, so a stored id keeps naming the task still to do, and the done line gets a new one (owner, 2026-11-16; the plugin writes the next occurrence with no id, so a tick in Obsidian itself still leaves the id on the done line; tasks waiting on the id (`⛔`) now wait on the next occurrence, which is what a series means; the next occurrence still loses its own `⛔`, as in the plugin); a task reached by line that has no id gets one with that write, so the line route converts as it goes (owner, 2026-11-16); a task reached by line that has an id is refused with `task_has_id`, naming the id, unless the id is shared (then only a line can pick one); `clear=["id"]` is refused. Off, ids are written only when given, and `id` addressing works for any task that has one. The server never adds ids on its own, outside a write an agent asked for: it would rewrite notes that may be open in Obsidian, which is how sync-conflict copies are made (owner, 2026-11-16).
- **Task links and block ids** (fork, owner's decision 2026-11-17): every result naming a task carries `open_url` (with `OPEN_NOTE_URL` set): `list_tasks`, the three writers (plus `next_occurrence_open_url`), `open_area` and the ledger's citing tasks. Obsidian's URI has no line parameter; it opens a heading or a block (`Note#^id`, sent as `%23%5E<id>` inside `{path}`, which the deployment's redirect page passes through). So with `TASKS_BLOCK_ID` (default off; on in this vault's deployment) the writers give a task with an id that id as its block id, ` ^<id>` at the end of the line (`ops.with_block_id`), and the link names it; a line with no block id gets its note's link. The owner chose a block id on every task over a heading link (lands in the section, not on the line) and over the Advanced URI plugin's `line=` (a line number goes stale when lines above move). A block link the line already has is kept (another note may link to it), unless it is the task's previous id: that one follows the id, so a recurring task ticked done hands its block id to its next occurrence with its id, and the done line takes its new id's, never leaving two lines with one block id. An id holding `_` (allowed in ids, not in block ids) gets none, and neither does a task whose id another line of the note already ends with as a block id (`ops.note_block_ids`): a note never gets two lines with one block id (both found by the adversarial review). Renaming an id (`new_id`) moves its block id with it, so a link another note copied to the old block (`Note#^old`) stops landing on the task: accepted, since the id is the task's name and a rename is asked for. A private task's link uses its block id only when it is the task's own id, which the result gives anyway; a block id written by hand is part of the text. Unverified (review): a task followed by a lazy continuation line, or inside a callout, may get a link that opens only the note. The script lists, and leaves, tasks whose id another task shares, whose id holds `_`, or whose note already has that block id. `scripts/fork_tasks_assign_ids.py --block-ids` adds them to an existing vault, run once (` ^<id>` before trailing spaces, every other byte kept, the same checks as the id conversion). (owner)
- **Made-up ids** are six lowercase letters and digits (`ids.new_id`, `secrets`), like the plugin dialog's, never all digits (it would read as a line number), and not one the vault already uses (this note from its text; other notes from the index, where each id drawn is looked up on its own: "Speed", below).
- **The conversion** (`scripts/fork_tasks_assign_ids.py`, run once over the owner's synced vault with Obsidian closed, owner's decision): every task without an id gets one, done tasks included. The id is added at the end of the line (before a block link and trailing spaces) and no other byte changes; the line must read back as the same task plus that id, and every other line of the note as before (the same scan as `edit_task`), or it is left without an id and listed. It does not use the tools' line writer, which re-serializes the whole line: the adversarial review found that rewriting would drop a field given twice or an unknown `🏁` value, so lines the tools refuse to rewrite are listed too. A dry run lists every change first. It skips hidden folders, symlinks, sync-conflict copies, notes that are not UTF-8 and notes with an unclosed indented fence, and leaves a note that changed between its read and its write; a stopped run is simply run again.

Limitations, accepted: a task written to a note in the last minutes by hand or on a device not yet synced is found by id only once indexed, or with its `path` (T4); a `path:line` an agent wrote down before the conversion still goes stale (nothing points at tasks by line in the vault itself: checked 2026-11-16).

## Areas

An area's tag is declared once, in its main note's frontmatter: `area_tag: area/<slug>` (owner's decision). The tools read the declarations from the index (`notes_metadata.frontmatter`). `list_tasks(area=…)` resolves a slug, a tag or the main note's name to `tags include #area/<slug>`; the folder never counts. `create_task(areas=…)` writes `#area/<slug>` tags; with `areas` omitted, a note inside an area's folder (the main note's folder; the deepest wins; a main note at the vault root claims nothing) gets that area's tag. An unknown, invalid or doubly declared area is refused, never turned into a new tag. `edit_task` keeps a task's area tags: a new `description` that leaves one out gets it back at the end, as `create_task` adds them, because an area tag says where the task belongs, not what it says, and an agent rewording a task moved it out of its area by accident (F108, 2026-11-17). Any `#area/…` tag the tools could have written counts (`#area/<slug>`, nested ones included, lowercase), declared or not; a tag is found where the plugin reads one, so `#area/x,` is that tag, and `areas=[]` that would leave only the global filter is refused. Declined after the adversarial review: tags written by hand in another case (`#Area/X`) are not area tags here, and a dropped-tag note compares case-sensitively; and a new description ending in a block link (`^abc`), refused before, is accepted when an area tag lands after it, the `^abc` staying plain text. `edit_task(areas=…)` replaces them (`[]` removes them all), resolved and refused like `create_task`'s. Other tags follow the description, since they are part of its wording (`#next`, `#when`), but the result's `notes` name each one a new description dropped. (AI suggestion)

## Dates

"Today" is the owner's local date in `TASKS_TIMEZONE` (default `Europe/Brussels`), never the server clock's day; the server refuses to start if the zone cannot be loaded. The image's own timezone database is used (the Python base image carries one); no extra package. Date arguments are `YYYY-MM-DD`, `today`, `tomorrow` or `yesterday`; the plugin's natural-language dates are not accepted, so an agent never depends on a parser it cannot see.

## The index

`fork_note_tasks` (migration 1001): one row per task line or problem of an indexed note — `note_id` (cascades with the note), `line_number` (1-based over the whole file), `kind`, the exact `line`, `reason`. The pass writes a changed or moved note's rows next to its links, in the same transaction, each note's insert in its own poison savepoint (site `fork-tasks`), a skip withholding the re-derive stamp exactly as a link skip does. `CURRENT_EXTRACTION_VERSION` 4 derived every existing note's rows once; it shares the version-3 cleaner, so nothing was re-embedded. Owner scoping is through `notes_metadata.user_id`, as for `note_links`.

## Choices made by the agent that built this (not requirements)

Recorded so they are never mistaken for the owner's rules; each can be changed.

1. **Rows store a line's text, not its meaning.** Status types, the global filter, file-name dates and "today" come from the settings and the clock, so `list_tasks` parses at query time; a settings change needs no reindex.
2. **Immediate re-index of the written note's task rows only.** After a write, the tool replaces that note's `fork_note_tasks` rows from the bytes it just published, in its own transaction under the index generation lock, waiting at most 5 s (`IMMEDIATE_INDEX_WAIT_SECONDS`); the note's other derived data waits for the next pass. The result says `indexed` and why not. **Until that pass, the note row's `notes_metadata.content_hash` lags the file.** No write precondition ever uses it: every write compares the caller's `expected_hash` with the hash of the bytes it reads from disk in that call, `list_tasks` returns the hash of the bytes it reads from disk, and a write returns the hash of the bytes it published. A note not yet in the index (a new inbox) gets its rows at the next pass. Change 2 (a file watcher with per-path passes) is where the tools would switch to a real per-note pass.
3. **`list_tasks` verifies returned lines on disk** (freshness, above).
4. **`create_task` creates a missing note only when it is the inbox** (`TASKS_INBOX_PATH`) with no heading, so a typo does not create a note.
5. **`create_task`'s `expected_hash` is optional**; it only adds a line, and the in-call compare covers its own read-to-write window.
6. **A rule outside upstream's list is refused, never passed through as written**, by `set_task_status` and `edit_task` alike: the plugin would rewrite it in rrule's wording on save, which cannot be reproduced for it.
7. **`list_tasks` defaults to `status="not_done"`**, shown in `query`; the plugin's own default is no filter.
8. **🆔 / ⛔ are written on the task being written only**: the plugin's dialog may also write another task's 🆔 for a dependency; the tools never change a second line (18).
9. **Statuses by name** (`todo`, `done`, `cancelled`, `in_progress`) mean the first registered status of that type; any other is by `symbol`; an unregistered symbol is refused (the plugin would invent an Unknown status).
10. **A global query is applied only when every line is one the tools implement**; otherwise `list_tasks` refuses.
11. **A description holding a field emoji is refused** on create (and on edit, unless the line already had one), because the plugin reads it as text, which is almost always an agent mistake.
12. **Writes refuse what changes another line's reading** (`verify_other_lines`), and an unpaired `%%` in a written line, though the plugin itself would write both.
13. **`area` overlap is reported, not refused**: `tags include #area/x` also matches `#area/x-y` (the plugin's meaning); `list_tasks` names the overlapping declared tags in `notes`.
14. **Path sorting approximates JS `localeCompare`** (case-insensitive, numeric runs as numbers) without ICU.
15. **`create_task` refuses a new recurring task with status done**: the plugin's dialog would write it and its next occurrence as two lines; create it, then tick it.
16. **A recurring task whose scheduled date comes from the file name is refused** when ticked: the date is not on the line, and the plugin's handling of it in a next occurrence is not ported.
17. **`set_task_status` reports the new occurrence** (`next_occurrence`, `next_occurrence_line`, a note that the lines below moved), so an agent acting on another task of the note knows its line changed; its `line`, `ref` and `text` stay the ticked task's, as for any other tick (found by the cold readers and the adversarial review: they read `line` as the ticked task's).
18. **🆔 and ⛔ are written on the task being written only, and checked against the vault.** `create_task` and `edit_task` take `id` (the plugin's characters, `[a-zA-Z0-9-_]+`) and `depends_on` (ids, written without spaces and once each, as the plugin writes them; on `edit_task` it replaces the list). The plugin's dialog, given a dependency on a task with no id, makes one up and writes it into that other task's line, possibly in another note; the tools never change a second line, so the agent gives that task an id first (`edit_task(…, new_id=…)`), then names it. Four refusals the plugin does not make, since each is almost always a mistake that would silently unchain or lock tasks, each naming the tasks concerned: an id another task already carries, done or not (ids are "intended to be unique across the whole vault", plugin docs, and the plugin blocks on any open task with the id, so a reused one could re-block); a changed or removed id that open tasks wait for (they would be unblocked without anyone asking); a new dependency on an id no task carries (it would block nothing); and a dependency that leads back to this task through open tasks waiting for one another (a cycle of any length, found by a walk over the open tasks' dependencies), checked for every dependency when the task takes a new id, since open tasks may already name that id (a dependency left dangling by `🏁 delete`, a hand edit or a deleted note). A finished task (DONE, CANCELLED or NON_TASK) waits for nothing and blocks nobody, as in the plugin's `Task.isBlocked` and `isBlocking`: a done waiter neither stops a rename nor closes a cycle, and a done task being written may change or clear its id, can't close a cycle and is never said to block anyone. Ticking a recurring task that carries 🆔 or ⛔ writes its next occurrence without them, as the plugin does, so a chain through the series ends there; the result says what the new occurrence lost and how to move the id across (clear it on the done line, whose id blocks no one, then set it on the new one); found by the review of the two branches' merge (2026-11-15). `set_task_status` runs none of these checks, so un-ticking a done task can close a cycle that was allowed while it was done: accepted, as the plugin allows it too and chains aren't in use here yet. When a new id is one open tasks already named, the write goes ahead and the result says they are now blocked by this task. `depends_on` on `edit_task` replaces the list, so the result names the ids a replacement left out. A dependency the task already had is otherwise kept unchecked, and a task can't depend on itself. The vault is read from the index for other notes and from the note's own text for the note written, so a task written in another note since the last pass is not seen: by hand or on a device not yet synced (T4), or by these tools to a note the index does not know yet, such as a new inbox (T10); the refusal of an unknown dependency says so.

## Speed

Measured on the deployment (an Intel Atom server, the vault on gocryptfs), a task write took 0.7 to 1.1 s. Four changes (2026-11-19) cut the reading and parsing, not what is decided:

- **A made-up id is looked up, not the vault's whole list of ids** (`_TaskIdMaker` in `tools.py`). Before, `create_task` (twice) and every `set_task_status` listed and parsed every indexed task carrying 🆔 or ⛔. Now the note's own ids come from its text, and each id drawn is looked up in the index by itself (`_task_ids_in_index` with `needles`: the database keeps the lines holding it, Python parses only those); a tick that makes no id reads nothing.
- **The id checks (`check_task_ids`) look other notes' tasks up by the ids the write sets, drops or adds**: the carriers and waiters of those ids are all they read, except the walk looking for a cycle (a new dependency on a task with an id), which can run through any task and keeps the whole list.
- **One call reads the Tasks settings once and scans each text once** (`_one_task_call` on the three write tools, `scan.one_call`): a write reached `_task_context` up to four times and scanned the same note up to ten times (finding the task, the note's ids, the read-back, the other lines' check, the re-index, the ledger citations), each with a YAML parse of the frontmatter. `scan_note` depends on the text alone and its result is immutable; nothing is kept between calls.
- **A task line is parsed once, then answered from a cache** (`ops.parse_line`, 2026-11-19): `list_tasks`, `open_area`, the ledger's task links and the id checks' whole list parse every indexed task line of the vault on each call, about 30 µs a line on a desktop (90 ms for 3,000 lines) and several times that on the server, most of `list_tasks`' 100-250 ms. `parse_task_line` is pure and a `Task` is frozen, so the parse is kept in a least-recently-used cache of `PARSE_CACHE_LINES` (20,000) lines, keyed by everything the parse reads: the line, the registered statuses, the global filter and the date the file name implies. A changed setting or line is a new key; an error is never kept. Unlike the scans above, this is kept between calls, for the process's life.

The lists of tasks a refusal names (`_refs`, at most five) come in the database's order, as before: no order was promised, and the narrower queries may return them in another one.
